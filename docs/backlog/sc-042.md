# [SC-042] WSL ambient proxy env bypasses px (autoProxy override + zsh profile gap)

**Status**: In Progress (2026-07-17)
**Priority**: High
**Component**: `lib/wsl/ops.ps1` (`Invoke-ConfigureWsl` autoProxy default), `lib/wsl/scripts/setup-proxy.sh` (cross-shell env block), `lib/wsl/proxy.ps1`, `lib/wsl/ops.Tests.ps1`, `docs/runbooks/px-proxy.md`
**Related**: [SC-040](sc-040.md) (Windows-side px tool), [SC-021](sc-021.md) (`.wslconfig` defaults that set `autoProxy=true`), [SC-036](sc-036.md) (WSL-side proxy setup)

**Summary**:
As a developer using px behind a Kerberos/NTLM corporate proxy, I want WSL's ambient proxy environment to point at the local px endpoint (`http://127.0.0.1:3128`) in every shell, so that native Linux tools (git, apt, pip, curl without `-x`) reach the internet through px with no stored credentials, instead of being pointed straight at the corporate proxy and getting `407`.

**Description**:
SC-040 shipped px on the Windows host and claimed WSL support. In practice, environment-driven tools inside WSL never use px: they hit the corporate proxy directly and get `407 Proxy Authentication Required`, which is the exact problem px exists to solve.

Confirmed live on the corporate network (2026-07-17), in a WSL zsh shell:

```
$ curl -sS -o /dev/null -w 'ambient -> %{http_code}\n' http://example.com
ambient -> 407
$ curl -sS -o /dev/null -w 'via px  -> %{http_code}\n' -x http://127.0.0.1:3128 https://www.google.com
via px  -> 200
$ curl -v http://example.com -o /dev/null 2>&1 | grep -i proxy
* Uses proxy env variable http_proxy == 'http://osde01proxy02.marquardt.de:8080'
* Connected to osde01proxy02.marquardt.de (192.168.98.9) port 8080
< HTTP/1.1 407 Proxy Authentication Required
< Proxy-Authenticate: Negotiate
< Proxy-Authenticate: Basic realm="Squid proxy-caching web server"
```

Two independent root causes make this happen:

1. **`autoProxy=true` injects the corporate proxy into WSL.** `Invoke-ConfigureWsl` (`lib/wsl/ops.ps1:363-368`) writes `autoProxy=true` into `%USERPROFILE%\.wslconfig` (introduced 2026-03-11 in SC-021, ~4 months before px). With `autoProxy=true`, WSL evaluates the Windows PAC and injects `HTTP_PROXY`/`http_proxy` = the corporate proxy plus `WSL_PAC_URL` into every shell's environment at init. This overrides any profile-based attempt to point WSL at px, and it is injected regardless of shell (that is why it appears in zsh, which never reads `~/.profile`).

2. **`setup-proxy.sh` writes only to `~/.profile`, which zsh does not read.** The managed env block (`lib/wsl/scripts/setup-proxy.sh:157-166`) is appended to `~/.profile`. bash login shells read it; zsh reads `~/.zshenv`/`~/.zprofile`/`~/.zshrc`, not `~/.profile`. So even with autoProxy disabled and "Local" (px) chosen in `setup-proxy`, a zsh user gets no px env at all.

**Why SC-040's WSL UAT passed anyway:** every WSL validation step (`sc-040.md:22`, `sc-040.md:62`) used `curl -x http://127.0.0.1:3128 ...`. The `-x` flag overrides the `http_proxy` environment variable, so those probes went to px regardless of the ambient env. The UAT proved px is *reachable* from WSL (mirrored networking works); it never exercised the environment path that real tools use. The conflict has been latent since px landed; the acceptance test bypassed it.

**Scope Decisions**:

- **DECISION NEEDED (autoProxy default):** `autoProxy=true` actively fights the px workflow, but it is helpful for non-px users on Basic auth (WSL auto-gets the corporate proxy). Options:
  - (a) Change the `.wslconfig` default to `autoProxy=false` (px-first); non-px users rely on `setup-proxy` Basic mode to write the corporate env.
  - (b) Keep `autoProxy=true` and document that px users must set it to `false`.
  - (c) Make `configure-wsl` parameterize/prompt for it.
- **DECISION NEEDED (existing-machine migration):** `Merge-WslConfig` never overwrites existing values, so flipping the default alone will NOT fix a machine that already has `autoProxy=true` written (including the reporter's own). Options: overwrite this one key specifically, prompt to flip it, or document a manual edit.
- **DECISION NEEDED (cross-shell env target):** where should `setup-proxy` write proxy env so both bash and zsh (and non-interactive login shells) see it? Candidates: `/etc/environment` (shell-agnostic, PAM login, but static `KEY=value`, system-wide), an additional `~/.zshenv`/`~/.zprofile` block, or `/etc/profile.d/`. Must stay idempotent with matching remove logic.

**Decisions taken** (2026-07-17): autoProxy default → **false** (px-first); existing-machine migration → **force-overwrite the `autoProxy` key** to the default; cross-shell env target → **`/etc/profile.d/wsl-manager-proxy.sh` sourced from `/etc/zsh/zshenv`**.

**Why not `/etc/environment`**: it is only loaded by `pam_env` during a PAM login, which the WSL shell-launch path bypasses (confirmed on the corporate machine: `su - $USER` sees the vars, a normal `wsl.exe` shell does not). `/etc/profile.d` is read by bash login shells and, on Debian/Ubuntu, by zsh login shells (`/etc/zsh/zprofile` sources `/etc/profile`); `/etc/zsh/zshenv` is read by every zsh, covering non-login shells. setup-proxy also migrates away any obsolete `/etc/environment` and `~/.profile` blocks.

**Acceptance Criteria**:
- [ ] With px running and chosen as the target, a WSL login shell exposes `http_proxy`/`HTTP_PROXY` pointing at `http://127.0.0.1:3128` (not the corporate proxy) in **both bash and zsh** (UAT)
- [ ] `curl https://www.google.com` **without `-x`** from WSL succeeds through px with no stored credentials, in both bash and zsh (UAT)
- [ ] The autoProxy/px conflict is resolved so WSL's ambient env is not silently overridden back to the corporate proxy (UAT confirms the runtime outcome)
- [x] Machines that already have `autoProxy` written to `.wslconfig` are handled, not just fresh ones: `Merge-WslConfig` force-overwrites `autoProxy` (unit-tested)
- [x] `setup-proxy.sh` writes and removes the proxy env in `/etc/profile.d/wsl-manager-proxy.sh` (sourced from `/etc/zsh/zshenv` for zsh), covering bash and zsh, idempotently; legacy `/etc/environment`, `~/.profile`, and `~/.bashrc` blocks are migrated away
- [x] Pester unit tests cover the changed `.wslconfig` default/overwrite behavior; the profile.d/zshenv writing/removal is asserted via `setup-proxy.sh` source tests (bash cannot be executed in the Pester harness; runtime is covered by UAT)
- [x] `docs/runbooks/px-proxy.md` documents the WSL/autoProxy interaction and the resulting WSL setup steps
- [ ] All existing tests continue to pass (CI green; local run has 17 environmental `setup-user` failures unrelated to this change)

**UAT Procedure** (corporate Windows machine, feature branch checked out):
1. [ ] With px running, run `configure-wsl` and `setup-proxy` (Local/px); open a fresh **bash** login shell: `curl -sS -o /dev/null -w '%{http_code}\n' http://example.com` → `200` (via px, no `-x`).
2. [ ] Repeat in a fresh **zsh** shell → `200`.
3. [ ] `env | grep -i proxy` in both shells shows `http_proxy=http://127.0.0.1:3128`, not the corporate proxy, and no stray `WSL_PAC_URL` forcing the corporate proxy.
4. [ ] Tear down (`setup-proxy` Remove): proxy env removed from both bash and zsh locations.
