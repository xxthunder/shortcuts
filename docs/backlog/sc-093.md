# [SC-093] ✅ DONE - The px-proxy runbook says that px 0.13.2 and later fall back like the browser

**Status**: Done (2026-11-19)
**Priority**: Low
**Component**: `docs/runbooks/px-proxy.md`

**Summary**:
As a px-proxy user with "Automatically detect settings" on, I want the runbook to say which px version falls back to the setup script and the manual proxy, so that I update px instead of changing my Windows proxy settings.

**Description**:
SC-091 documented that px 0.13.1 asks WPAD only when "Automatically detect settings" is on, and connects directly when WPAD finds nothing. SC-092 took the fix upstream: [genotrance/px#291](https://github.com/genotrance/px/pull/291) merged on 2026-11-18, and px 0.13.2, released on 2026-11-19, lists it under Bug fixes: "On Windows, Px falls back from WinHTTP auto-detect to PAC and then the Internet Options manual proxy, honouring its `*.domain` and `<local>` bypass entries". The Scoop Main bucket has 0.13.2, so `px-proxy install` and `scoop update px` get it.

The runbook still says that px does not fall back and that this holds for px 0.13.1. "How discovery works" and the `504 Gateway Timeout` troubleshooting section describe the gap as current.

**Scope Decisions**:
- **Docs only** (2026-11-19): px-proxy installs px through Scoop without a version pin, so no code changes. SC-092 decided that px-proxy does not wait for the release.
- **The 0.13.1 behaviour stays as a note** (2026-11-19): a machine that has not updated px still runs the old version, so the runbook names both versions and tells the user how to update.

**Acceptance Criteria**:
- [x] "How discovery works" says that px 0.13.2 and later fall back from auto-detect to the setup script and then to the manual proxy with its bypass list, and that px 0.13.1 asks WPAD only.
- [x] The `504 Gateway Timeout` section tells the user to check the px version and update px first.
- [x] `uv run poe docs` passes.
