# [SC-065] Devcontainer for development and tests on Linux

**Status**: Open
**Priority**: Medium
**Component**: `.devcontainer/` (new), a test script under `test/bin/` (new)
**Related**: [SC-064](sc-064.md) (its tests ran in an ad-hoc pwsh container), [SC-060](sc-060.md) (its UAT fixes were pushed without a local test run)

**Summary**:
As a developer, I want one container definition for shortcuts that I can open with DevPod on a Linux host and that agents can use to run lint and unit tests, so that the tooling lives in the repository instead of being rebuilt by hand for every change.

**Description**:
Work on shortcuts from Linux hosts (the DevVM `picard`, agent sessions) has used throw-away containers: a pwsh image with Pester and PSScriptAnalyzer, plus separate runs for shellcheck, faketime and Structurizr. That tooling is a project need and belongs in the repository.

Two uses, one image:

- **Development**: a `devcontainer.json` that runs under DevPod on `picard` and on a WSL, with the corporate CA handled the way other devcontainers do it (the host provides the certificates, the image trusts them) and Claude Code installed in `postCreate`.
- **Tests for agents**: a script that runs lint and the unit tests in the same image, without VS Code or DevPod.

The repository stays Windows-first. Integration tests against real WSL cannot run in the container, and the CI on Windows remains the authority. 58 unit tests fail on Linux on `develop` (2026-10-01) because they need Windows (for example `Copy-WslDistro` paths, `robocopy`, `.lnk` shortcuts). Until they are handled, a Linux run only means something compared with `develop`: a failure counts when it is new on the branch.

The ad-hoc image is not enough because nothing in the repository points to it. On 2026-10-01 an agent session that had started in another repository fixed SC-060 UAT findings, found no `pwsh` on the host and pushed to CI without running the unit tests. The image `sc060-pwsh` was on the host the whole time. An agent reads `AGENTS.md` and the `powershell-test-exec` skill; both only show the Windows command (`pwsh -File .\test\bin\testrunner.ps1 -Unit`).

The ad-hoc image, as a starting point:

```dockerfile
FROM mcr.microsoft.com/powershell:7.5-ubuntu-24.04
RUN pwsh -NoProfile -Command "Set-PSRepository PSGallery -InstallationPolicy Trusted; Install-Module Pester -MinimumVersion 5.7.1 -MaximumVersion 5.99 -Force -SkipPublisherCheck -Scope AllUsers; Install-Module PSScriptAnalyzer -MinimumVersion 1.24 -Force -Scope AllUsers"
```

```bash
docker run --rm --user $(id -u):$(id -g) -e HOME=/tmp -e CI=1 -v "$PWD:/repo" -w /repo \
  sc060-pwsh pwsh -NoProfile -File test/bin/testrunner.ps1 -Unit
```

`-TestPath <file>` runs one file, `-LintOnly` only PSScriptAnalyzer.

Raised on 2026-09-30.

**Open Questions**:
- **Windows-only tests**: tag them and skip the tag on Linux, or keep a list of known Linux failures? A tag keeps the Linux run green but changes test files.
- **Base image**: `mcr.microsoft.com/devcontainers/base:bookworm` with the PowerShell feature, like other devcontainers, or the official `mcr.microsoft.com/powershell` image?
- **Container runtime inside**: docker-outside-of-docker for the Structurizr viewer and container-based tests, or leave it out?
- **Tools in the image**: which of shellcheck, faketime and the Structurizr CLI belong in it?

**Acceptance Criteria**:
- [ ] `.devcontainer/` builds and starts under DevPod on a Linux host; pwsh, Pester and PSScriptAnalyzer work inside
- [ ] A script runs lint and the unit tests in the same image, from a Linux shell, with a clear pass or fail result
- [ ] The Windows-only unit tests are handled as decided, so a clean tree gives a clean Linux run
- [ ] The corporate CA works in the container when the host provides it; without it the build still succeeds
- [ ] The docs say how to open the devcontainer and how to run the tests in it
- [ ] The Quick Reference in `AGENTS.md` and the `powershell-test-exec` skill name the Linux command next to the Windows one, so an agent on a Linux host finds it
