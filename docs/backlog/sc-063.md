# [SC-063] setup-docker fails on WSL 3.0 at systemd-binfmt

**Status**: Open
**Priority**: High
**Component**: `lib/wsl/scripts/install-docker.sh` (step 8.6, WSL interop via binfmt.d)
**Related**: [BUG-002](bug-002.md) (moved the WSL interop registration from rc.local to binfmt.d and systemd-binfmt)

**Summary**:
As a developer whose Windows got WSL 3.0, I want `setup-docker` to configure WSL interop without failing, so that Docker installs and the CI is green again.

**Description**:
Since 2026-09-29 the CI runner (image `windows-2025-vs2026` 20260925.250.1) gets WSL 3.0.1.0 with kernel 6.18.40.1-1 from `wsl --update` in `test/bin/init.ps1`; the last green run had WSL 2.7.14.0 with kernel 6.18.33.2-2. Since then `install-docker.sh` fails in step 8.6:

- `sudo systemctl restart systemd-binfmt` ends with "Job for systemd-binfmt.service failed because the control process exited with error code", the script logs "Failed to configure WSL interop via binfmt.d" and exits with 3.
- The integration tests "Should install or verify Docker and all components (idempotent)" and "Should configure binfmt.d for WSL interop (not rc.local)" fail.
- The failure is the same on `develop` and on every PR branch since then. A tree that passed on 2026-09-28 fails now. The Debian packages and systemd (257.13-1~deb13u1) are the same in the green and the red runs, so WSL 3.0 is the change.
- The kernel still reports the WSLInterop registration ("Kernel WSLInterop registration: registered").

Why `systemd-binfmt` fails under WSL 3.0 is not known yet: the CI log shows only the failed job, not its status or journal. A user whose WSL updates to 3.0 hits the same failure on `setup-docker`.

Found on 2026-09-29 while checking the CI of PR #90 (SC-060).

**Scope Decisions**:
- **Diagnostics first**: when the restart fails, the script prints `systemctl status systemd-binfmt` and `journalctl -xeu systemd-binfmt` before it exits, so the next CI run shows the cause. The fix follows from that.
- **WSL 2.x keeps working**: the fix must not break distributions on WSL 2.x.

**Open Questions**:
- Does WSL 3.0 register WSLInterop in a way that makes systemd-binfmt's own registration fail, for example because the entry already exists?
- Is `binfmt_misc` mounted or managed differently in WSL 3.0?
- Is the restart needed at all when the kernel already reports WSLInterop as registered?

**Acceptance Criteria**:
- [ ] When the systemd-binfmt restart fails, `install-docker.sh` prints the unit status and its journal before it exits
- [ ] The root cause is found and recorded here
- [ ] `setup-docker` succeeds on WSL 3.0 and still on WSL 2.x
- [ ] The Docker integration tests are green in CI again
