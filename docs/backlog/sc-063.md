# [SC-063] setup-docker fails on WSL 3.0 at systemd-binfmt

**Status**: In Progress
**Priority**: High
**Component**: `lib/wsl/scripts/install-docker.sh` (step 8.6, WSL interop via binfmt.d)
**Related**: [BUG-002](bug-002.md) (moved the WSL interop registration from rc.local to binfmt.d and systemd-binfmt)

**Summary**:
As a developer whose Windows got WSL 3.0, I want `setup-docker` to configure WSL interop without failing, so that Docker installs and the CI is green again.

**Description**:
Since 2026-09-29 the CI runner (image `windows-2025-vs2026` 20260925.250.1) gets WSL 3.0.1.0 with kernel 6.18.40.1-1 from `wsl --update` in `test/bin/init.ps1`; the last green run had WSL 2.7.14.0 with kernel 6.18.33.2-2. Since then `install-docker.sh` fails in step 8.6:

- `sudo systemctl restart systemd-binfmt` ends with "Job for systemd-binfmt.service failed because the control process exited with error code", the script logs "Failed to configure WSL interop via binfmt.d" and exits with 3.
- The integration tests "Should install or verify Docker and all components (idempotent)" and "Should configure binfmt.d for WSL interop (not rc.local)" fail.
- The failure is the same on `develop` and on every PR branch since then. A tree that passed on 2026-09-28 fails now. The Debian packages and systemd (257.13-1~deb13u1) are the same in the green and the red runs, so WSL 3.0 is the change.
- The kernel still reports the WSLInterop registration ("Kernel WSLInterop registration: registered").

Why `systemd-binfmt` fails under WSL 3.0 is not known yet: the CI log shows only the failed job, not its status or journal. A user whose WSL updates to 3.0 hits the same failure on `setup-docker`.

Found on 2026-09-29 while checking the CI of PR #90 (SC-060).

**Root Cause**:
WSL 3.0 makes `/proc/sys/fs/binfmt_misc/status` read-only inside every distribution, and `systemd-binfmt` exits with an error whenever it cannot write that file.

- WSL [PR #40621](https://github.com/microsoft/WSL/pull/40621) ("protect binfmt_misc from cross-distro wipe at shutdown") bind-mounts `/run/wsl/binfmt-status-lock` read-only over `/proc/sys/fs/binfmt_misc/status` in the mount namespace of each distribution, switched by `[boot] protectBinfmt` (default `true`). It stops the `systemd-shutdown` of one distribution from wiping the kernel-global registry, and with it WSLInterop, for every other running distribution. WSL registers WSLInterop itself with the `F` flag (`:WSLInterop:M::MZ::/init:FP`).
- The same PR removed the drop-in WSL 2.x generated at `/run/systemd/generator/systemd-binfmt.service.d/override.conf`: an empty `ExecStop=` and an extra `ExecStart=` that re-registered WSLInterop.
- `systemd-binfmt` without arguments first flushes all rules by writing `-1` to `status`. Under WSL 3.0 that write fails with `EROFS`. systemd logs "Failed to flush binfmt_misc rules, ignoring: Read-only file system", but keeps the error as its result (`RET_GATHER` keeps the first error), applies the `binfmt.d` files anyway and exits 1. The code is the same in systemd 257.13 (Debian 13) and in systemd `main`.
- So on WSL 3.0 `systemd-binfmt.service` is `failed` after every boot of a systemd distribution and every `systemctl restart systemd-binfmt` fails, while the `binfmt.d` rules are registered. This matches the CI: "Kernel WSLInterop registration: registered", Windows interop works, `systemctl is-active systemd-binfmt` reports `failed`.
- WSL 3.0.1 contains #40621, 2.7.14 does not. WSL [issue #41226](https://github.com/microsoft/WSL/issues/41226) shows the same journal on the pre-release 2.9.4; the WSL team calls the failure benign.

Every CI run on WSL 3.0.1.0 is red and every run on 2.7.14.0 is green. Run 36680402555 (2026-09-30, PR #90) is green only because `wsl --update` failed there with `Wsl/UpdatePackage/0x80190193` (HTTP 403) and the runner stayed on 2.7.14.0: whether the CI is green depends on whether that update succeeds.

The cause is derived from the WSL 3.0.1 and systemd 257.13 sources and the version correlation in CI; the diagnostics of AC 1 confirm it once a CI run on WSL 3.0 shows the `EROFS` line in the journal.

**Scope Decisions**:
- **Apply the rule, do not restart the unit**: step 8.6 runs `systemd-binfmt /etc/binfmt.d/WSLInterop.conf`. Given a file, `systemd-binfmt` registers that rule and does not flush, so it works on WSL 2.x and 3.0 alike. On failure it prints its own error to stderr, which reaches the CI log; this replaces the planned dump of `systemctl status` and `journalctl`, which the root cause made unnecessary.
- **The kernel entry counts, not the unit**: neither the script nor the integration test checks the state of `systemd-binfmt.service`, which is `failed` after every boot on WSL 3.0. Both check that `/proc/sys/fs/binfmt_misc/WSLInterop` reports `enabled`.
- **Rejected**: `[boot] protectBinfmt=false` would bring back the wipe of WSLInterop in every distribution when one systemd distribution shuts down; pinning WSL in CI would hide the failure that users on WSL 3.0 hit.
- **WSL 2.x keeps working**: the fix must not break distributions on WSL 2.x.

**Open Questions**:
- Does WSL 3.0 register WSLInterop in a way that makes systemd-binfmt's own registration fail, for example because the entry already exists? No: the registration succeeds; the flush before it fails (see Root Cause).
- Is `binfmt_misc` mounted or managed differently in WSL 3.0? Yes: `status` is a read-only bind mount in each distribution, WSL registers WSLInterop with `F`, and the WSL drop-in for `systemd-binfmt.service` is gone.
- Is the restart needed at all when the kernel already reports WSLInterop as registered? No: `systemd-binfmt /etc/binfmt.d/WSLInterop.conf` applies that one file without the flush (see Scope Decisions). Checked with systemd 257.13 and a read-only bind mount over `status`: without arguments it exits 1, given the file it exits 0 and the entry reads `enabled`.

**Acceptance Criteria**:
- [ ] When applying the WSLInterop rule fails, `install-docker.sh` shows the reason before it exits
- [ ] The root cause is found and recorded here
- [ ] `setup-docker` succeeds on WSL 3.0 and still on WSL 2.x
- [ ] The Docker integration tests are green in CI again
