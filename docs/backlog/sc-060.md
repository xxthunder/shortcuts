# [SC-060] Install the corporate root CA into a WSL distribution

**Status**: Open
**Priority**: Medium
**Component**: `lib/wsl/` (new `ca.ps1` and `scripts/setup-ca.sh`, following `proxy.ps1` and `scripts/setup-proxy.sh`), `docs/wsl-manager.md`, `docs/runbooks/px-proxy.md`
**Related**: [SC-043](sc-043.md) (CA variables that assume the CA is trusted), [SC-042](sc-042.md) (proxy env), [SC-040](sc-040.md) (px)

**Summary**:
As a developer on a machine behind a TLS-inspecting corporate proxy, I want WSL Manager to put the corporate root CA into the distribution's trust store, so that a freshly set up distribution reaches HTTPS through px without a manual copy step.

**Description**:
The corporate proxy inspects TLS and presents certificates signed by the corporate root CA. Everything WSL Manager sets up for that case assumes the CA is already trusted inside the distribution, but no command puts it there:

- SC-043 points `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE` and `PIP_CERT` at `/etc/ssl/certs/ca-certificates.crt`. That only helps if the bundle contains the corporate CA.
- `docs/runbooks/px-proxy.md` says so explicitly: "This assumes the corporate root certificate authority (CA) is already trusted system-wide", and under Troubleshooting: "for WSL, into the distro's CA bundle".
- Dev containers built in the distribution copy the host's `/usr/local/share/ca-certificates/*.crt` into the image (the `initializeCommand` pattern of the ESE repositories). With no CA there, the image trusts nothing extra and every TLS request through the inspection fails.

Today the CA gets there by hand: the user copies the certificate into `/usr/local/share/ca-certificates/` and runs `update-ca-certificates`. That is the one step of the setup in `docs/wsl-manager.md` that the tool does not cover and the docs do not describe.

Found on 2026-09-27 while documenting the dev container setup of the ESE repositories on the company machine.

**Scope Decisions**:
- **Target location is `/usr/local/share/ca-certificates/` plus `update-ca-certificates`.** It is the Debian/Ubuntu way to add a local CA, the system bundle SC-043 points at is rebuilt from it, and dev containers already read the host's certificates from there.
- **Idempotent**, like every other wsl-manager command: running it twice leaves the same state.
- **Removal is part of the item**: the command must be able to take its certificates out again (analogous to `setup-proxy` Remove).
- **Own command `setup-ca`, not part of `setup-proxy`.** TLS inspection needs the CA with or without px. `setup-proxy` keeps setting the CA variables (SC-043) and keeps assuming the CA is there.
- **The certificates come from the Windows certificate store** (`Cert:\LocalMachine\Root`), not from a file passed by path: Windows already trusts the corporate root CA, so wsl-manager exports it itself. They are written as PEM `.crt` files, the format `update-ca-certificates` reads.
- **Selection by subject pattern.** CLI: `setup-ca <distro> -Subject <pattern>`, a PowerShell wildcard matched against the certificate subject. The TUI asks for the pattern, lists the matching certificates and asks for confirmation. A pattern that matches nothing is an error and changes nothing.
- **Root certificates only, one or more.** No intermediates.
- **Managed files are named `wsl-manager-<thumbprint>.crt`.** Install makes the managed set equal to the selection: it adds what is missing and deletes managed certificates that are no longer selected, so a rotated root CA is replaced by running the command again. Remove deletes all `wsl-manager-*.crt` and nothing else, then rebuilds the bundle.

**Acceptance Criteria**:
- [x] Open Questions answered and recorded as Scope Decisions
- [ ] `setup-ca` (TUI and CLI) exports the root certificates matching a subject pattern from the Windows store into `/usr/local/share/ca-certificates/` of a distribution and runs `update-ca-certificates`
- [ ] A pattern that matches no certificate fails without changing the distribution
- [ ] The same command removes the certificates it installed (`wsl-manager-*.crt`), and only those
- [ ] Running it twice leaves the same state (idempotent); running it with a changed selection replaces the managed certificates
- [ ] Unit tests cover install, repeat, changed selection, no match and removal without touching the real `wsl.exe`
- [ ] `docs/wsl-manager.md` has the step in DevContainer Setup (before Step 4, Configure Proxy) and in the Commands Reference; `docs/runbooks/px-proxy.md` points to it instead of assuming the CA
- [ ] UAT on the corporate machine: on a fresh distribution, after this command and `setup-proxy`, `curl https://www.google.com` and `uv python install 3.12` succeed through px
