# [SC-060] ✅ DONE - Install the corporate root CA into a WSL distribution

**Status**: Done (2026-10-01)
**Priority**: Medium
**Component**: `lib/wsl/` (new `ca.ps1` and `scripts/setup-ca.sh`, following `proxy.ps1` and `scripts/setup-proxy.sh`), `docs/wsl-manager.md`, `docs/runbooks/px-proxy.md`
**Related**: [SC-043](sc-043.md) (CA variables that assume the CA is trusted), [SC-042](sc-042.md) (proxy env), [SC-040](sc-040.md) (px)

**Summary**:
As a developer on a machine behind a TLS-inspecting corporate proxy, I want WSL Manager to put the corporate root CA into the distribution's trust store, so that a freshly set up distribution reaches HTTPS through px without a manual copy step.

**Description**:
The corporate proxy inspects TLS and presents certificates signed by the corporate root CA. Everything WSL Manager sets up for that case assumes the CA is already trusted inside the distribution, but no command puts it there:

- SC-043 points `SSL_CERT_FILE`, `SSL_CERT_DIR`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE` and `PIP_CERT` at `/etc/ssl/certs/ca-certificates.crt`. That only helps if the bundle contains the corporate CA.
- `docs/runbooks/px-proxy.md` says so explicitly: "This assumes the corporate root certificate authority (CA) is already trusted system-wide", and under Troubleshooting: "for WSL, into the distro's CA bundle".
- Dev containers built in the distribution copy the host's `/usr/local/share/ca-certificates/*.crt` into the image (the `initializeCommand` pattern of the ESE repositories). With no CA there, the image trusts nothing extra and every TLS request through the inspection fails.

Today the CA gets there by hand: the user copies the certificate into `/usr/local/share/ca-certificates/` and runs `update-ca-certificates`. That is the one step of the setup in `docs/wsl-manager.md` that the tool does not cover and the docs do not describe.

Found on 2026-09-27 while documenting the dev container setup of the ESE repositories on the company machine.

**Scope Decisions**:
- **Target location is `/usr/local/share/ca-certificates/` plus `update-ca-certificates`.** It is the Debian/Ubuntu way to add a local CA, the system bundle SC-043 points at is rebuilt from it, and dev containers already read the host's certificates from there.
- **Idempotent**, like every other wsl-manager command: running it twice leaves the same state.
- **Removal is part of the item**: the command must be able to take its certificates out again (analogous to `setup-proxy` Remove).
- **Own command `setup-ca`, not part of `setup-proxy`.** TLS inspection needs the CA with or without px. `setup-proxy` keeps setting the CA variables (SC-043) and keeps assuming the CA is there.
- **The certificates come from the Windows certificate store** (`Cert:\LocalMachine\Root`), not from a file passed by path: Windows already trusts the corporate root CA, so wsl-manager exports it itself. They are written as PEM `.crt` files, the format `update-ca-certificates` reads.
- **Manual selection by subject pattern** (TUI: Install, then Manual). CLI: `setup-ca <distro> -Subject <pattern>`, a PowerShell wildcard matched against the certificate subject. The TUI asks for the pattern, lists the matching certificates and asks for confirmation. A pattern that matches nothing is an error and changes nothing.
- **Auto detection by URL** (TUI: Install, then Auto; added 2026-09-29): the root of the certificate chain Windows builds for an HTTPS request to the URL. The request is a HEAD through the .NET `HttpClient`, which uses the system proxy including PAC and the Windows logon for proxy authentication. It therefore finds the TLS-inspection root through the corporate proxy, and the root of an internal PKI for an intranet site (git, Jira) that PAC sends direct. The default URL is `https://www.google.com`; a bare host name gets `https://`. The TUI asks for further URLs in a loop and collects the roots without duplicates before one confirmation; the CLI takes `-Url` with one or more URLs.
- **Only roots Windows trusts are installed**: a detected root must be in `Cert:\LocalMachine\Root` and not expired, otherwise that URL fails with a message naming the root. A public site without TLS inspection yields a public root; the listing shows it before the confirmation.
- **The probe is a small C# class loaded with `Add-Type`**: `HttpClient` runs its certificate callback on a thread without a PowerShell runspace, so a scriptblock cannot serve as that callback.
- **Root certificates only, one or more.** No intermediates.
- **Managed files are named `wsl-manager-<thumbprint>.crt`. Install adds** (changed 2026-09-29, was: replace the managed set): it writes the selected certificates and keeps the other managed ones, so Auto can run for several sites one after another. Every run deletes managed certificates that have expired (`openssl x509 -checkend 0`; openssl comes with `ca-certificates`), which is how a rotated root CA leaves. Remove deletes all `wsl-manager-*.crt` and nothing else, then rebuilds the bundle.
- **CLI**: `setup-ca <distro> -Url <url>[,<url>...]` (Auto) and `setup-ca <distro> -Subject '<pattern>'` (Manual) install without a prompt; `setup-ca <distro> -Remove` removes. More than one of the three is an argument error. Without any, the command asks interactively; in CI it only warns.
- **TUI**: the menu entry is **Setup CA certificates (corporate)**, directly before **Setup proxy (corporate)**; menu search finds it by "ca" and by "cert" (changed 2026-10-01 after the UAT, was: Setup root CA (corporate)). Flow: distribution, then Install / Remove / back; Install then Auto / Manual / back; then the URLs or the pattern, the list of roots, and a confirmation.
- **Confirmation by consequence** ([ADR 0004](../architecture/adr/0004-wsl-manager-confirmations-follow-the-consequence.md); changed 2026-10-01 after the UAT, was: `[y/N]` for both): Install only adds wsl-manager's own files and can be repeated, so it asks `[Y/n]` with `Get-UserConfirmation`, as `setup-proxy` does. Remove takes the trust away and every HTTPS request through the inspection fails until the next install, so it stays `[y/N]` with `Confirm-DestructiveAction`.
- **Expired certificates are never selected** from the Windows store, in Auto and Manual alike.
- **No match is an error** whose message suggests the pattern with wildcards (`*<pattern>*`).
- **A pattern that is too broad fails** with a request to narrow it, before the arguments would exceed the Windows command-line limit (30 000 characters).
- **Transport**: the certificates travel to the script as `--cert=<THUMBPRINT>:<base64 DER>` arguments; no temporary files, no Windows paths.
- **Missing `ca-certificates` in the distribution fails** with exit code 1 and a clear message; the command does not install the package.
- **`update-ca-certificates` is called by its full path** (`/usr/sbin/update-ca-certificates`), because `/usr/sbin` is not on a non-root user's `PATH` on Debian. Running as root, the script does without `sudo`.
- **No terminate**: unlike `setup-proxy`, `setup-ca` leaves the distribution running; the rebuilt bundle is read on the next TLS connection.
- **Quiet trust store rebuild** (added 2026-09-30 after the UAT): `setup-ca.sh` shows the output of `update-ca-certificates` only when it fails. Its warnings on every run (a bundle file with more than one certificate, duplicates of a CA installed another way) are normal and only confuse users who know nothing about CAs.
- **A CA installed by hand before is left alone** ([ADR 0002](../architecture/adr/0002-wsl-manager-changes-only-what-it-marked.md)): it is then trusted twice, which does no harm. The docs say how to remove the old copy so that wsl-manager manages the CA alone.

### UAT Procedure

On the corporate machine, behind the TLS-inspecting proxy, with px running and shortcuts on this branch. Have one intranet HTTPS site at hand (git or Jira).

1. Install a fresh distribution and set up its user: `.\tools\wsl-manager\wsl-manager.ps1 install Ubuntu-24.04`, then `.\tools\wsl-manager\wsl-manager.ps1 setup-user Ubuntu-24.04`. Expected: both succeed.
2. Run `tools\wsl-manager\wsl-manager.bat`, select **Setup CA certificates (corporate)**, pick the distribution, choose **Install**, then **Auto**, and press Enter for `https://www.google.com`. Expected: the corporate TLS-inspection root is shown with expiry and thumbprint, not a public CA. Answer `y` to checking another URL and enter the intranet site. Expected: its root is shown, or the same root again, which is then listed once. Answer `N`. Expected: the collected roots are listed with a `[Y/n]` prompt; after Enter the success line names their count.
3. In the distribution run `ls /usr/local/share/ca-certificates`. Expected: one `wsl-manager-<thumbprint>.crt` per root from step 2, nothing else changed.
4. Run `.\tools\wsl-manager\wsl-manager.ps1 setup-proxy Ubuntu-24.04` and choose px. In a new shell of the distribution run `curl -sS -o /dev/null -w '%{http_code}\n' https://www.google.com` and the same for the intranet site, install uv if missing (`curl -LsSf https://astral.sh/uv/install.sh | sh`), then `uv python install 3.12`. Expected: no certificate error, and Python 3.12 installs.
5. Run `.\tools\wsl-manager\wsl-manager.ps1 setup-ca Ubuntu-24.04 -Url https://www.google.com`. Expected: no prompt, a success line; `ls -l --time-style=full-iso /usr/local/share/ca-certificates` shows the same files with unchanged times, including the intranet root.
6. Run `.\tools\wsl-manager\wsl-manager.ps1 setup-ca Ubuntu-24.04 -Subject '<Company>'` (no wildcards). Expected: an error that suggests `'*<Company>*'`; the files are unchanged.
7. Run `.\tools\wsl-manager\wsl-manager.ps1 setup-ca Ubuntu-24.04 -Url https://www.google.com -Remove`. Expected: an argument error; the files are unchanged.
8. Run `.\tools\wsl-manager\wsl-manager.ps1 setup-ca Ubuntu-24.04 -Remove`, then the `curl` for google.com from step 4 in a new shell. Expected: no `wsl-manager-*.crt` left, and `curl` fails with a certificate error. Repeat step 5. Expected: `curl` returns `200` again.
