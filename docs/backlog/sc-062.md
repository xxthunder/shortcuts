# [SC-062] Document the repository architecture as a C4 model in Structurizr DSL

**Status**: In Progress
**Priority**: Medium
**Component**: `docs/architecture/` (new Structurizr DSL workspace), `docs/architecture/wsl-manager-c4.md` (replaced), `docs/architecture/README.md`
**Related**: [SC-016](sc-016.md) (produced `wsl-manager-c4.md`)

**Summary**:
As a maintainer of this repository, and as an agent working in it, I want one C4 model of the whole repository written in Structurizr DSL, from which every diagram is generated, so that the views stay consistent with each other and cover more than WSL Manager.

**Description**:
The only architecture diagrams today are the three hand-written Mermaid diagrams in `docs/architecture/wsl-manager-c4.md` (system context, container, component), written for SC-016. Each diagram repeats the elements it shows, so every change has to be made in several places by hand, and the diagrams drift apart from each other and from the code.

The rest of the repository has no architecture documentation at all: the bootstrap and install path (`bin/install.ps1`), the Scoop update helper (`lib/scoop`, `tools/scoop`), the proxy tooling (`tools/proxy`: px and `setProxy.ps1`), the launcher integration (`links/`, `tools/flow-launcher`), AutoHotKey, the Claude Code and Git hook tooling, and the shared libraries under `lib/`.

The C4 model as Simon Brown presents it, with Structurizr as the modelling tool (GOTO Copenhagen 2026), separates the model from its views: every element and relationship is defined once in a Structurizr DSL workspace, and each diagram is a view onto that model. The Structurizr CLI exports views to Mermaid, PlantUML and other formats; Structurizr Lite is archived, and its successor is the `local` command of the `structurizr/structurizr` image.

**Scope Decisions**:
- **The whole repository is modelled**, not only WSL Manager.
- **The Structurizr DSL workspace is the single source of the architecture diagrams.** The hand-written Mermaid C4 diagrams are replaced, not kept alongside.
- **Not in scope**: changes to existing code, and C4 level 4 (code).
- **Viewing is local for now**: the views are read with the `local` command of the `structurizr/structurizr` image. Exported views for GitHub and Obsidian, and a CI check that keeps them current, are follow-up work.
- **Viewer scripts**: `tools/structurizr/structurizr-local.sh` starts the container with `docker` or `podman`, whichever is available, mounts `docs/architecture`, serves port 8080 by default and runs in the foreground until Ctrl+C. `structurizr-local.ps1` with a `.bat` wrapper runs that script in a WSL distribution (the default one, or `-Distro`) and opens the browser once the port answers.
- **A container is a unit that runs on its own**: the installer and updater (`bin/`), WSL Manager, the distribution scripts (Bash inside WSL, a runtime of their own), the Scoop update helper, the proxy tools, AutoHotKey, the tool installers under `tools/`, and the launcher catalog (`links/`) as a data store. Libraries under `lib/` are components of the containers that dot-source them.
- **Components and views**: components are modelled for WSL Manager and its distribution scripts only. Views: system context, containers, and for WSL Manager one view per user goal (manage distributions; prepare a distribution for dev containers; configure WSL globally) plus one overview of all its components. Use-case based component views follow Simon Brown's recommendation.
- **Files**: `workspace.dsl` and the layout file `workspace.json` that `local` writes live in `docs/architecture/` and are committed; the `.structurizr/` working directory is ignored.
- **Layout by hand, later**: the views have no `autolayout`. Their elements are arranged in Structurizr local, which saves the positions in `workspace.json`. Arranging them is follow-up work; until then every element of a view starts at the top left.
- **Not in this item**: `!docs` and `!adrs` (the ADRs here do not follow the adr-tools format the default importer expects); MCP and the `design-record` and `architecture-scan` skills; and the ADR on the tool choice, which waits until LikeC4 has been evaluated as an alternative.

**Acceptance Criteria**:
- [x] Open Questions answered and recorded as Scope Decisions
- [ ] One Structurizr DSL workspace under `docs/architecture/` models the whole repository at the levels decided
- [ ] The WSL Manager views show at least what `wsl-manager-c4.md` shows today, for every module in `lib/wsl/`
- [ ] The views can be read where the decision says, and `wsl-manager-c4.md` is removed or replaced by generated output
- [ ] `docs/architecture/README.md` explains how to view the model and how to change it
- [ ] `structurizr-local` starts the viewer from Windows (`.bat`) and from a Linux or WSL shell (`.sh`)
- [ ] Unit tests cover the PowerShell wrapper without touching the real `wsl.exe`; the Bash script is shellcheck clean
