# [SC-084] A release branch holds only the files users need

**Status**: In Progress
**Priority**: High
**Component**: `.github/workflows/` (new release job), `lib/`, `tools/proxy/`, `tools/scoop/`, `tools/wsl-manager/`, `LICENSE`, `AGENTS.md`

**Summary**:
As the maintainer of a downstream fork that vendors this repository as a git subtree, I want an orphan branch `release` that holds only the files users need, updated on every push to `develop`, so that the fork takes the tools without their tests, CI, docs and agent configuration.

**Description**:
A downstream fork vendors this repository with `git subtree` (squashed) and starts px-proxy, WSL Manager and the Scoop update helper from it. Today the subtree takes `develop` as a whole: tests, `.github/`, `.claude/`, docs and tools the fork never starts all land in its tree, and its users and reviewers have to tell them apart. A reviewer of the fork suggested a release branch that holds only what users need, like the "external components" concept of the fork's organisation.

The fork keeps the subtree; it only changes the branch it pulls from to `release` and tracks its tip. Testing stays here: the fork runs no unit tests of the vendored code, only a UAT.

What the fork uses, at today's paths:
- `tools/proxy/` (`px-proxy.bat`, `px-proxy.ps1`, `setProxy.ps1`), which loads `lib/utils/utils.ps1`
- `tools/scoop/` (`update-scoop.bat`, `update-scoop.ps1`), which loads `lib/scoop/scoop.ps1`
- `tools/wsl-manager/` (`wsl-manager.bat`, `wsl-manager.ps1`), which loads `lib/wsl/manager.ps1`; the fork's own setup script also sources `lib/utils/utils.ps1` and `lib/wsl/manager.ps1` and calls `Invoke-WslCommand` and `Set-WslConf`
- `LICENSE`, since the fork redistributes the code under MIT

**Scope Decisions**:
- **An orphan branch, updated on every push to `develop`** (the maintainer's call, 2026-11-04): `release` shares no history with `develop`; each update is one commit on `release` that names the `develop` commit it was built from. The fork tracks the tip, not tags.
- **Only after green tests**: the release job runs after the test job of the same push and only when it passed, so `release` never takes a red `develop`.
- **An allow-list decides what goes in**: a file in this repository lists the paths that `release` holds, and the job copies exactly those. A new file reaches `release` only when someone adds it to the list, so tests, CI and docs never slip in by accident. The check in the release job (see the criteria) catches a file the tools need that the list misses.
- **Paths stay as on `develop`**: the fork's launchers and scripts call files by path, so `release` keeps the folder layout and only leaves files out.
- **No tests on `release`**: `*.Tests.ps1`, `*.Integration.Tests.ps1` and `test/` stay on `develop`, where CI runs them.
- **A short `README.md` on `release`**: it says what the branch is, that it is built by CI and must not be edited, and points to `develop`.
- **All of `lib/` goes to `release`** (the maintainer's call, 2026-11-04), without its test files: the tools and the fork's own scripts load from it, so the allow-list names the folder, not single files. That takes in `lib/wsl/scripts/*.sh`, the shell scripts WSL Manager copies into a distribution.
- **`.gitattributes` goes to `release`**: the shell scripts must stay LF and the `.bat` and `.ps1` files CRLF in the fork's working tree too, and a nested `.gitattributes` in the subtree folder does that.
- **Where it lives**: `bin/release/` holds the allow-list `paths.txt`, the branch's `README.md` and the scripts `Build-Release.ps1`, `Test-Release.ps1`, `Publish-Release.ps1`, and `load-check.ps1`, which `Test-Release.ps1` runs in a child pwsh so the check sees only the functions of the release tree.
- **`lib/AGENTS.md` stays on `develop`**: it guides development here, not users.
- **`PwshSpectreConsole` needs nothing on the list**: `lib/wsl/spectre.ps1` offers to install the module when it is missing, so every caller of `lib/wsl/manager.ps1` gets the prompt. Nothing in `config/` is read by the three tools.
- **The check loads instead of starting the tools** (the maintainer's call, 2026-11-04): none of the three tools can be started harmlessly in CI (update-scoop is interactive, px-proxy test needs a running px), so the job loads `lib/utils`, `lib/scoop` and `lib/wsl/manager.ps1` from the built tree and checks every path built from `$PSScriptRoot` or `%~dp0`; an integration test runs the same on every pull request.
- **Own scripts, not a publish action**: `peaceiris/actions-gh-pages` (`publish_branch`, `force_orphan`) and `JamesIves/github-pages-deploy-action` (`branch`, `folder`) publish a folder to a branch, but neither is tested locally with Pester, neither skips an older source commit, and both would hold `contents: write` as third-party code.
- **`release` never goes backwards**: a source commit older than the one on `release` makes no commit, because a slower run of an older push can finish after a newer one.

**Acceptance Criteria**:
- [ ] A push to `develop` updates the orphan branch `release` with one commit that names the source commit of `develop`
- [ ] `release` holds exactly the paths of the allow-list: the three tools listed above, all of `lib/` without its test files and without `lib/AGENTS.md`, `LICENSE`, `.gitattributes` and its own `README.md`, at the same paths as on `develop`, and no tests, CI, docs or agent configuration
- [ ] The release job runs only when the tests of the same push passed
- [ ] A check in the release job loads `lib/utils`, `lib/scoop` and `lib/wsl/manager.ps1` from the built tree and confirms that every path a script builds from `$PSScriptRoot` or `%~dp0` exists, so a missing file fails the job; an integration test runs the same build and check on every pull request
- [ ] `git subtree pull --prefix=<dir> --squash <url> release` in a fork brings the update in
- [ ] `AGENTS.md` says what `release` is, how it is built, and that it must not be edited by hand
- [ ] All existing tests continue to pass
