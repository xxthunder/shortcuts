# [SC-082] px-proxy sets the proxy variables in the user environment

**Status**: Open
**Priority**: Medium
**Component**: `tools/proxy/px-proxy.ps1`, `tools/proxy/px-proxy.Tests.ps1`, `tools/proxy/setProxy.ps1`, `docs/runbooks/px-proxy.md`
**Related**: [SC-067](sc-067.md) (px starts at logon), [ADR 0005](../architecture/adr/0005-px-starts-at-logon-from-the-last-config.md)

**Summary**:
As a developer behind the corporate proxy, I want `HTTP_PROXY` and `HTTPS_PROXY` to point at px in my Windows user environment, so that every new process uses px without running `setProxy.ps1` in each shell first.

**Description**:
Today `setProxy.ps1` sets `HTTP_PROXY`/`HTTPS_PROXY` for the current session only. A tool started from Keypirinha, Explorer or a fresh shell does not see px and either fails with `407` or has to be pointed at px by hand. Since SC-067, px already runs after every logon, so the variables could live in the user environment (`HKCU\Environment`) as well.

The obvious chicken-and-egg problem is already solved: the upstream lookup in `start` (`Get-ProxyFromPac`) would otherwise read the px variables and report px as the corporate proxy. `Suspend-ProxyEnvVar` in `setProxy.ps1` clears them before the process's first system-proxy resolution, and user environment variables reach the process the same way the session ones do. Tests must still prove this for the user-environment case.

Installing px is no problem: `scoop install px` (or `uv`) reaches the internet through the corporate proxy, without px. The user only has to run `px-proxy stop` first when the variables still point at a px that is not running.

What is still open:

- **px becomes a hard dependency.** With session variables, a new shell without px still works. With user variables, every new process goes through px, also after `stop`, without the VPN, or with an outdated `px.ini` abroad (the cost ADR 0005 accepts).
- **`NO_PROXY`.** `Set-NoProxyEnvironment` sets only `localhost`. With user variables, intranet hosts would also go through px and the corporate proxy.
- **Only new processes see the change.** Running processes, Keypirinha included, keep their old environment until restarted or until the next logon.

WSL is not affected: `autoProxy=false` and `setup-proxy` already point it at px.

**Scope Decisions**:
- The variables follow px's lifecycle. `start` writes them to the user environment; `stop` and `remove` delete them. After a `stop`, new processes no longer go through px and fall back to the corporate proxy.
- `stop` always deletes the variables, also when px is not running or was never started. It is the user's way back to the corporate proxy, for example before installing px or another tool.

**Open Questions**:
- Which hosts go into the user `NO_PROXY`, and how do intranet hosts get there without naming a company in this repository (compare the open question in [SC-081](sc-081.md))?
- Does `setProxy.ps1` still need to set the session variables when px runs, or does it only check them?
- Should the variables be lowercase as well (`http_proxy`), as some tools read only those?

**Acceptance Criteria**:
- [ ] `start` writes `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` to the user environment and notifies running processes of the change
- [ ] `stop` and `remove` delete exactly the variables `start` wrote, and leave other user variables alone
- [ ] With the px variables in the user environment, `start` still resolves the corporate upstream proxy, not px
- [ ] `stop` deletes the variables also when px is not running or was never started
- [ ] `docs/runbooks/px-proxy.md` says which variables `start` sets, when new processes see them, and that `stop` removes them and so returns new processes to the corporate proxy
- [ ] Unit tests cover write, delete and the upstream lookup with the variables set, without touching the real user environment
- [ ] All existing tests continue to pass
