# [SC-051] ✅ DONE - px-proxy runbook: fix Keypirinha invocation, document manual start and VPN ordering

**Status**: Done (2026-07-29)
**Priority**: Medium
**Component**: `docs/runbooks/px-proxy.md`

**Summary**:
As a contributor following the px-proxy runbook, I want the "Usage" section to describe how Keypirinha actually invokes the tool, and I want the doc to tell me that px has to be started manually (and, when a VPN is required, only after the VPN is up), so that I don't try to run a `.ps1` file from Keypirinha (which cannot execute it) and don't start px against the wrong network path.

**Description**:
Two problems were reported against `docs/runbooks/px-proxy.md`:

1. **Wrong Keypirinha invocation.** The "Usage" section says "Run from Keypirinha (type `px-proxy`) or from a terminal" and then shows a single code block invoking `px-proxy.ps1` directly. Keypirinha's file catalog (`config/keypirinha/portable/Profile/User/filescatalog.ini`) only indexes `.url .lnk .cmd .bat .exe` — `.ps1` is not in that list, confirmed by checking the config — so Keypirinha cannot discover or run the `.ps1` file at all. This is exactly the scenario the project's PowerShell Script Wrapper Convention (`AGENTS.md`) exists for: `px-proxy.bat` already exists (`tools/proxy/px-proxy.bat`) and is what Keypirinha actually resolves and runs when you search `px-proxy`. The doc needs to say that explicitly instead of implying the `.ps1` invocation applies to both paths.
2. **No mention that px must be started manually.** There is currently no persistent installation, scheduled task, or other automation that starts px on logon or reboot — the user has to run the `start` action themselves every session. The doc doesn't say this anywhere.
3. **No VPN ordering guidance.** For setups where a VPN is required to reach the corporate network (e.g. home office), px must be started *after* the VPN connection is established — proxy discovery (PAC evaluation) and the Kerberos ticket both depend on the corporate network being reachable, so starting px first resolves against the wrong (unreachable) path.

**Scope Decisions**:
- **Docs only.** No code, `.bat`, or `.ps1` changes — `px-proxy.bat` already exists and already does the right thing; the runbook just described it incorrectly.
- **Match the existing `wsl-manager.md` pattern**: that doc separates "search for `<tool>` in Keypirinha" from the terminal-specific `.ps1 <command>` invocation, rather than presenting one code block as covering both. Apply the same separation here.
- **No automation is being added** for auto-starting px on logon/VPN-connect; SC-051 only documents the current manual reality. Building that automation, if wanted, is a separate future backlog item.

**Acceptance Criteria**:
- [x] "Usage" section no longer implies the `.ps1` file can be run from Keypirinha; it states Keypirinha resolves/runs `px-proxy.bat` (matching the `.bat` wrapper convention), with the `.ps1` form documented as the terminal invocation
- [x] A note states px does not start automatically: no persistent installation/scheduled task exists, and `start` must be run manually each session
- [x] A note states that when a VPN is required to reach the corporate network, px must be started after the VPN connection is established, with the reason (proxy discovery and the Kerberos ticket both need the corporate network reachable)
- [x] No other runbook content changed
