# [SC-073a] PowerShell support in sphinx-codelinks

**Status**: In Progress
**Priority**: Medium
**Component**: upstream: `packages/sphinx-codelinks/` in [useblocks/sphinx-needs](https://github.com/useblocks/sphinx-needs)

**Summary**:
As the maintainer, I want sphinx-codelinks to read one-line need markers in PowerShell files, Pester tests included, so that the px-proxy code and its tests can trace to their requirements.

**Description**:
sphinx-codelinks 2.0.1 reads C and C++, Python, C#, TypeScript and JavaScript, YAML, Rust, Go, JSONC and Bash. File types are tied to a comment type by a fixed table (`source_discover/config.py`); a `.ps1` file is skipped, and no configuration adds it. The parsers are tree-sitter grammars; a PowerShell grammar is on PyPI as `tree-sitter-powershell` (0.26.4, from Airbus CERT). Bash was added the same way (`FE_BASH`).

codelinks lives in the useblocks/sphinx-needs monorepo. ubCode has its own Rust implementation (`rust/ubc_codelinks`), kept equal by a parity test: the shared YAML extraction fixtures in `tests/data/extraction/` and their snapshots are copied into ubCode byte for byte. The fixtures and snapshots are therefore the contract; the Rust side is useblocks' work.

**Scope Decisions**:
- **What the pull request holds**: a `powershell` comment type for `.ps1`, `.psm1` and `.psd1`; `#` line comments and `<# #>` block comments; markers associated with function definitions; fixtures and snapshots for the shared extraction tests; an `FE_POWERSHELL` feature need with its fault needs in `docs/components/features.rst`; `IMPL_` markers in the new source; documentation and a changelog entry; green `uv run poe lint` and `uv run poe typecheck`.
- **A Pester `It` is a scope**: a marker above an `It` annotates that test, as a marker above a function annotates the function.
- **To raise with useblocks**: a marker above an `It` could get the Pester path of its block (`Describe.Context.It`, the case name Pester writes to JUnit) as a field. The test need would then match its result (SC-073d) without the marker repeating the path.
- **The pull request is the author's**: useblocks closes generated pull requests without review. AI assistance is fine when the author has read and tested the change and answers for it; the pull request template asks for that.
- **Comment-based help** (`.SYNOPSIS` blocks): whether a marker inside it counts is settled with useblocks.
- **Raised in person**: the change was raised with useblocks at the user day on 2026-10-23, where they welcomed it; that counts as raising it (author's decision). The work happens in the fork `xxthunder/sphinx-needs`.
- **Merged through useblocks' own pull request** (2026-11-12): useblocks/sphinx-needs#2506 carries the three commits of #2380 unchanged, with useblocks' review commits on top (`3295bd621` on `master`); #2380 was closed. ubCode gets the same behaviour from useblocks/ubcode#4750, which shares the extraction fixtures. Where useblocks changed the design:
  - an `It` is entity kind `test`, a `Describe` or `Context` is `namespace`;
  - in a pipeline (`a | b`, `a && b`) a marker binds the first command that is an entity;
  - in PowerShell, `@{` and `@(` never open a marker, so a one-line need's title cannot start with `{` or `(`;
  - comment-based help first in a function's body documents that function (`doc_comment`);
  - scope modifiers are dropped from function names, Pester blocks honour `-Name` and skip Pester's own leading parameters;
  - an attribute before a class or enum stops a marker above it from binding (documented limitation).
- **The pin moves to the release, not to `master`** (author, 2026-11-14): shortcuts stays on `sc-073a-preview-3` until a sphinx-codelinks release carries #2506; moving the pin is a code change and goes through a pull request.

**Technical Notes**:
- `tree-sitter-powershell` 0.26.4 is MIT licensed, needs Python 3.10 or newer, and ships wheels for Linux (glibc and musl), macOS and Windows on x86_64 and arm64. Its grammar (ABI 15) loads with the `tree-sitter~=0.25.1` codelinks pins (probed 2026-10-23).
- Node types: `#` and `<# #>` comments are both `comment`; a function is a `function_statement`; Pester's `Describe`, `Context` and `It` are plain `command` nodes with a `script_block` argument, so an `It` scope is a `command` whose command name is `It`.
