# [SC-066] wsl-manager hands the Linux side of a distribution to Ansible

**Status**: Open
**Priority**: Medium
**Component**: `lib/wsl/docker.ps1`, `lib/wsl/podman.ps1`, `lib/wsl/devpod.ps1`, `lib/wsl/wsl-conf.ps1`, `tools/wsl-manager/`, `docs/wsl-manager.md`
**Related**: [SC-061](sc-061.md) (setup-proxy and the apt, Docker and Podman files it writes), [SC-065](sc-065.md) (devcontainer on Linux hosts)

**Summary**:
As a developer, I want wsl-manager to prepare a distribution and then hand it to the Ansible role that sets up my Linux development hosts, so that a WSL distribution and my DevVM get their tools from one definition instead of two.

**Description**:
Decision by the repository owner on 2026-10-01. Two places install the same tools today:

- wsl-manager installs Docker, Podman and DevPod into a distribution with its own shell scripts (`setup-docker`, `setup-podman`, `setup-devpod`).
- An Ansible role, `dev-stack`, today in the owner's home-lab repository, installs Docker, DevPod, zsh and an apt upgrade on the DevVM `picard`.

The role moves into its own public repository, `xxthunder/ansible-role-dev-stack`. A second public repository, `xxthunder/xxthunder-workbench-setup`, holds a bootstrap that installs Ansible on the local host and runs the role against it; it carries the role as a git submodule. The same bootstrap sets up a WSL distribution and the DevVM, at home and on the corporate machine.

wsl-manager keeps what only Windows can do and what has to happen before the first package is installed:

| Task | Owner after this item |
|---|---|
| `.wslconfig`; install, clone and remove a distribution; user account | wsl-manager |
| Corporate root CA and proxy | wsl-manager: they come before the first `apt` and need the Windows certificate store and px |
| `wsl.conf` | wsl-manager |
| SSH config sync with Windows | wsl-manager |
| Install Ansible and run the `dev-stack` bootstrap | wsl-manager (new) |
| Docker, Podman, DevPod, apt upgrade | the `dev-stack` role |

A distribution an agent works in is meant to be a boundary. `Set-WslConf` can write any section, but no command turns `automount` and `interop` off; the example in its help turns `interop` on.

`Install-WslPodman` goes the other way: as "Podman prerequisites" it writes `interop` with `enabled = true` and `appendWindowsPath = true`, and `automount` with `options = metadata,umask=022`, next to `systemd = true` and the boot command `mount --make-rshared /`. Podman itself moves to the role, rootless and set up the way `install-podman.sh` does it today; `systemd` and the boot command are `wsl.conf` and stay here.

**Scope Decisions**:
- wsl-manager installs no container runtime and no DevPod any more; the role does.
- Corporate CA and proxy stay in wsl-manager and run before the bootstrap.

**Open Questions**:
- Do `setup-docker`, `setup-podman` and `setup-devpod` disappear, or does each become a call to the bootstrap with the runtime as a parameter?
- Does wsl-manager clone `xxthunder/xxthunder-workbench-setup` inside the distribution, or copy the bootstrap in?
- Does rootless Podman need `interop` at all, or only `systemd` and the boot command? If not, the Podman prerequisites and `interop` off do not conflict.
- `automount` and `interop` off: for every distribution, or only for one an agent works in? With `automount` off, `/mnt/c` is gone; check which wsl-manager steps read Windows files from inside the distribution.
- What happens to `manager.docker.Integration.Tests.ps1` and `manager.podman.Integration.Tests.ps1`?

**Acceptance Criteria**:
- [ ] A fresh distribution with CA and proxy gets Podman and DevPod through the `dev-stack` bootstrap, and a DevPod workspace builds and runs in it
- [ ] wsl-manager contains no shell script that installs Docker, Podman or DevPod
- [ ] wsl-manager can turn `automount` and `interop` off for a distribution
- [ ] `docs/wsl-manager.md` describes the new DevContainer setup steps

Raised on 2026-10-01.
