# [SC-067] ✅ DONE - px starts at logon

**Status**: Done (2026-10-19)
**Priority**: Medium
**Component**: `tools/proxy/px-proxy.ps1`, `tools/proxy/px-proxy.Tests.ps1`, `lib/utils/utils.ps1`, `lib/utils/utils.Tests.ps1`, `docs/runbooks/px-proxy.md`, `docs/architecture/workspace.dsl`, `docs/architecture/adr/` (new ADR)
**Related**: [SC-040](sc-040.md) (decided "No autostart"; this item reverses that decision), [SC-051](sc-051.md) (runbook: manual start and VPN ordering)

**Summary**:
As a developer behind the corporate proxy, I want px to start when I log on to Windows, so that Claude Code and other tools work after a reboot without a manual `px-proxy start`.

**Description**:
px runs only after `px-proxy start`. After a reboot the user often forgets it, and the first session that needs the proxy (Claude Code, for example) fails. The runbook says so: "px does not start itself".

SC-040 chose "No autostart; Keypirinha-launched on demand" and gave no reason beyond on-demand use. Its config decision states a concern that applies here: `start` resolves the proxy fresh "to avoid stale proxy hosts when roaming networks". For this user the concern does not hold. The upstream proxy has been the same host (`osde...`) for years, as long as the user stays in Germany. The `px.ini` from the last `start` therefore stays valid across reboots, and px can start from it at logon.

The logon start must not do what `start` does. The laptop usually starts outside the company network, and the user connects the VPN after logon. At logon, neither the PAC lookup nor the klist fallback can reach the company network, so a lookup at logon would fail or write a wrong `px.ini`. The logon start therefore launches px with the existing `px.ini` and nothing else.

Raised on 2026-10-19.

**Scope Decisions**:
- **`start` registers the logon start**: after `start` has launched px, it writes the logon entry. Each `start` overwrites the entry, so it always points to the px that `start` used. A `start` that fails before it launches px writes no entry and leaves an existing entry as it is.
- **The logon start never looks up the proxy**: the entry runs `pxw.exe --config="<data dir>\px.ini"` directly. No pwsh, no PAC lookup, no klist, no rewrite of `px.ini`, no key-press prompt. When the proxy changes, for example outside Germany, the user runs `start` by hand.
- **`stop` deletes the entry**: the entry follows the last command. After `start`, px runs now and at each logon; after `stop`, it runs neither now nor at the next logon. A user who stops px on purpose does not want it back after a reboot. Only the `stop` command deletes the entry, not the shared `Stop-PxProxy` function: `start` calls `Stop-PxProxy` to restart px and must keep the entry.
- **`remove` deletes the entry**: `remove` undoes everything the tool set up.
- **Startup folder, not a Run key or a scheduled task**: the entry is `px-proxy.lnk` in the user's Startup folder (`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`). A shortcut can set the working directory, which is where px writes its log when `log = 3`; a Run key value cannot. The user sees the entry in Task Manager > Startup apps and can turn it off there. `bin/install.ps1` already uses the Startup folder for the AutoHotkey entry. A scheduled task that runs a full `start` when the VPN connects would also cover a changing proxy, but it costs more, and it is not needed while the proxy host stays the same.
- **Logon start functions in `lib/utils/`**: finding the Startup folder, writing the entry and deleting it is not specific to px. `lib/utils/utils.ps1` provides `Get-AutostartPath`, `Register-Autostart` and `Unregister-Autostart`; px-proxy only passes its entry name, its executable, its config and its data folder. `Register-Autostart` writes the entry with `New-ShortcutFile`, which sets the target, the arguments and the working directory. `New-Shortcut` in `bin/install.ps1` sets only the target, and `install.ps1` must stay self-contained, so it keeps its own copy.
- **No opt-out switch**: there is no `-NoAutostart` flag. The user turns the entry off with `stop` or in Task Manager.

**Technical Notes**:
- On the author's laptop, `pxw` resolves to a uv tool install (`%USERPROFILE%\scoop\persist\uv\tools\shims\pxw.exe`), not to the Scoop `px` app. The entry uses whatever `Get-PxExecutable -Windowless` returns, the same executable that `start` uses.
- `start` launches pxw with `-WindowStyle Hidden`. A shortcut cannot hide its window. If the resolved `pxw.exe` is a console program, a window shows at logon. UAT step 2 checks this.
- It is not verified that px, started before the VPN, authenticates once the VPN is up. The expectation is that px connects upstream per request and that Windows gets the Kerberos ticket on first use. UAT step 4 checks this.

**UAT Procedure** (on the corporate laptop, with the feature branch checked out):

1. [x] Connect to the company network or the VPN. Run `px-proxy start`. Expect `px-proxy.lnk` in the Startup folder.
2. [x] Reboot. Log on without the company network. Expect px to run (`Get-Process pxw`), and expect no console window at logon. Expect the entry in Task Manager > Startup apps.
3. [x] Connect the VPN.
4. [x] Run `px-proxy test` without a `start` before it. Expect success.
5. [x] Run `px-proxy stop`. Expect no `px-proxy.lnk` in the Startup folder.
6. [x] Reboot. Expect px not to run.
