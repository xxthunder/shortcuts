# [SC-091] px finds the upstream on site when Windows has both auto-detect and a PAC URL

**Status**: Open
**Priority**: High
**Component**: `tools/proxy/px-proxy.ps1`, `tools/proxy/px-proxy.Tests.ps1`, `docs/runbooks/px-proxy.md`, `docs/requirements/px-proxy.md`

**Summary**:
As a user on a company site, I want px to find the corporate proxy when Windows has both "Automatically detect settings" and a PAC URL set, so that my command-line tools and WSL reach the internet without pinning an upstream with `-ProxyHost`.

**Description**:
Since SC-087, `start` without `-ProxyHost` writes `px.ini` with neither `server` nor `pac`, so px asks Windows for the upstream. On the author's machine at headquarters on 2026-11-16 (wired, no VPN) this fails: every request through px ends in `504 Gateway Timeout` after 20 seconds. Pinning the upstream (`server = osde01proxy02.marquardt.de:8080`, which the pre-SC-087 PAC lookup wrote) works.

Cause, found in px 0.13.1 (`px/wproxy.py`, `Wproxy.__init__` and `winhttp_find_proxy_for_url`):

- px reads `WinHttpGetIEProxyConfigForCurrentUser` and takes exactly one mode: `fAutoDetect` wins over `lpszAutoConfigUrl`, which wins over the manual proxy.
- In `MODE_AUTO` px calls `WinHttpGetProxyForUrl` with `WINHTTP_AUTOPROXY_AUTO_DETECT` only (DHCP and DNS WPAD), never with the PAC URL.
- When WPAD fails (`WINHTTP_ERROR_WINHTTP_AUTODETECTION_FAILED`), px logs "Autodetection failed, trying DIRECT instead" and connects directly. On site the firewall drops direct connections, hence the timeout.

On the author's machine all three Windows options are on: `DefaultConnectionSettings` flags byte `0x0F` (manual proxy, PAC URL `http://os-proxypac-dl.marquardt.de:8081/proxy-OS.pac`, auto-detect). `wpad` does not resolve at headquarters. The settings come from company group policy (`gpresult` lists `MQ_Browser-W11-ProxySettings` and `MQ_Browser-W11-OSProxy-3-PAC`), so colleagues of the downstream fork have the same settings and the user cannot simply untick auto-detect. Browsers keep working because WinINet falls back from WPAD to the PAC URL; px does not.

Reproduced on 2026-11-16 with a second px on port 3129, a `px.ini` without `server` and `pac`, `log = 4` and `--test=https://www.google.com`: the log shows `Proxy mode = MODE_AUTO`, the DIRECT fallback and the timeout. Not checked: why the same setup worked on VPN the day before (WPAD may resolve through the VPN's DNS).

The README of the downstream fork and the runbook now say px keeps working when the user moves between office, home and VPN. On site with these settings it does not.

Directions, not decided:

- **Fix px upstream**: in `MODE_AUTO`, also pass the PAC URL (`WINHTTP_AUTOPROXY_AUTO_DETECT | WINHTTP_AUTOPROXY_CONFIG_URL`), or fall back to it before `DIRECT`, as WinINet does. px-proxy then stays as it is; until a px release has it, users on site need a workaround.
- **`start` writes `pac = <AutoConfigURL>`** read from the Windows settings: px then uses its own PAC engine (`MODE_CONFIG_PAC`), which skips WPAD. SC-087 records why that engine is avoided: with home Wi-Fi and VPN it can resolve the PAC's host check against the home address and answer `DIRECT`. The PAC URL must also be reachable wherever px runs.
- **Workaround now**: `px-proxy start -ProxyHost osde01proxy02.marquardt.de:8080`. It loses what SC-087 gained: px no longer follows network changes.

**Acceptance Criteria**:

- [ ] Home Wi-Fi plus VPN still works without restarting px, as SC-087 requires.
- [ ] The chosen direction and the reason are recorded under Scope Decisions.
