# [SC-083] Format and lint each PowerShell file as soon as Claude changes it

**Status**: In Progress
**Priority**: Medium
**Component**: `PSScriptAnalyzerSettings.psd1`, `.claude/settings.json`, `tools/claude-hooks/`, `test/bin/linter.Tests.ps1`, `.vscode/settings.json`
**Related**: none

**Summary**:
As the author working with Claude Code, I want each PowerShell file that Claude edits to be formatted and linted right away, so that a lint finding is fixed in the same step and not at commit time.

**Description**:
PSScriptAnalyzer already lints in CI (`testrunner.ps1` through `linter.Tests.ps1`) and in the pre-commit hook, with the default rules at Warning and Error severity and no settings file. Nothing formats. A finding surfaces only at commit time or in CI, long after the edit that caused it.

Claude Code runs `PostToolUse` hooks after each tool call. A hook on `Edit` and `Write` that formats the changed file and reports the lint findings back to Claude closes that gap. Claude runs in WSL, so the hook needs `pwsh` and PSScriptAnalyzer there.

Raised on 2026-10-27.

**Scope Decisions**:
- **CodeFormatting preset** (author, 2026-10-27): `Invoke-Formatter` applies the PSScriptAnalyzer `CodeFormatting` preset, without its casing rule (see below). One settings file at the repository root, `PSScriptAnalyzerSettings.psd1`, holds the rules. The formatter, the hook and `linter.Tests.ps1` all read it, so CI fails on unformatted code.
- **One bulk reformat** (author, 2026-10-27): the existing `.ps1`, `.psm1` and `.psd1` files are formatted once, in a commit of their own that changes nothing else. `.git-blame-ignore-revs` lists that commit. The repository merges by rebase, which rewrites commit hashes, so the file is added after the merge, with the hash the commit has on `develop`.
- **`.git-blame-ignore-revs` goes straight to `develop`** (author, 2026-10-30): an exception to the rule that only `.md` changes may skip a pull request. The file holds one hash and changes no code, the unit tests and the linter do not read it, and it can only be written after the merge.
- **No casing rule** (author, 2026-10-30): the settings switch `PSUseCorrectCasing` off, unlike the preset. To find a command's casing, the rule resolves the command on a thread without a runspace; for a command of PwshSpectreConsole that fails, because the module's `RenderableTransformationAttribute` is a PowerShell class. `Invoke-Formatter` then fails on `lib/wsl/manager.ps1` and `lib/wsl/commands.ps1` wherever the module is installed, in CI as in the hook. The rule reports at Information severity anyway, below the lint threshold, so it never failed CI; casing is neither fixed nor checked.
- **Formatting keeps the encoding**: the hook writes a file back as UTF-8 with BOM and with CRLF line endings, as `AGENTS.md` and `.gitattributes` require. Any line ending it reads, a lone CR included, becomes CRLF.
- **A file that is not valid UTF-8 stays untouched** (author, 2026-10-30): the hook does not format it and exits with code 2, so Claude learns that the file needs to be saved as UTF-8 with BOM. Rewriting it would replace each undecodable byte.
- **Findings go to Claude**: when lint findings remain after formatting, the hook exits with code 2 and prints them, so Claude sees them and fixes them. A clean file produces no output.
- **The hook script is PowerShell**: `tools/claude-hooks/format-powershell.ps1`, run with `pwsh -NoProfile`, so it works in WSL and on Windows. It sits under `tools/` because the test runner searches only `tools`, `test`, `bin` and `lib`.
- **No Windows directories on PATH under WSL**: the hook drops the `/mnt/...` entries from `PATH` before it runs PSScriptAnalyzer. With them, PSScriptAnalyzer resolves commands across the WSL file system boundary, and one run takes about 50 seconds; without them it takes about 2. Command-dependent rules can therefore judge differently in WSL than in CI, and CI on Windows decides.
- **`pwsh` in WSL** comes from the Microsoft apt repository. PSScriptAnalyzer 1.24.0 or later and Pester 5 are installed for the user.
- **The hook is tested in-process**: the logic is the function `Invoke-FormatPowerShellHook`, and the script reads its input from `$input`. The tests call the function and pipe into the script, so Codecov sees every line; one test still runs the script in its own `pwsh` process, as Claude Code does.
- **VS Code formats like the hook** (author, 2026-10-27): the PowerShell extension formats on save with its own `powershell.codeFormatting.*` settings, not with `PSScriptAnalyzerSettings.psd1`. `.vscode/settings.json` sets `pipelineIndentationStyle`, the one that differs from `PSScriptAnalyzerSettings.psd1`, and four spaces for indentation; `useCorrectCasing` stays at its default, off, as in the settings file.

**Acceptance Criteria**:
- [x] `PSScriptAnalyzerSettings.psd1` exists and holds the `CodeFormatting` rules on top of the current default rules
- [x] `linter.Tests.ps1` and the pre-commit hook lint with that settings file, and the unit tests and the linter pass
- [x] All `.ps1`, `.psm1` and `.psd1` files are formatted in one commit that changes nothing else
- [x] After the merge, `.git-blame-ignore-revs` names that commit by its hash on `develop`
- [ ] An `Edit` or `Write` by Claude on a PowerShell file formats it, and the file keeps its BOM and CRLF line endings
- [ ] A lint finding after an edit reaches Claude through exit code 2; a clean file produces no output
- [x] An edit on any other file type does not run the formatter
- [x] The hook has Pester tests
- [x] VS Code formats a PowerShell file on save as the hook does
