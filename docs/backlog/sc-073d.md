# [SC-073d] Pester test results linked to their tests

**Status**: In Progress
**Priority**: Medium
**Component**: `ubproject.toml`, `conf.py`, `docs/test-results.md` (new), `docs/traceability/px-proxy.md`, `docs/runbooks/px-proxy.md`, `docs/index.md`, `tools/proxy/px-proxy.Tests.ps1`, `.github/workflows/test.yml`
**Depends on**: [SC-073b](sc-073b.md), [SC-073e](sc-073e.md)

**Summary**:
As the maintainer, I want every Pester result in the JUnit report to link the test it resulted from, and every test and requirement to show whether it is untested, not run, passed or failed, so that the documentation tells a tested requirement from a verified one.

**Description**:
The levels are those of ASPICE and of useblocks/SPLed: a requirement, the tests that point to it (codelinks markers, SC-073e), and the results that point to their test.

ubCode (since 0.37.0, beta) and sphinx-test-reports 3.x read JUnit XML directly: the `test-file` directive and its siblings, configured in the `[test_reports]` section of `ubproject.toml`. Each test case in `test/out/junit.xml` becomes a result need. Pester names a case by its full path, `Describe.Context.It` (its `ExpandedPath`), with the test file's container name as class name; it writes no properties and no tags on a test case.

The link from result to test is therefore derived by matching: a `join` rule (sphinx-needs 9.1.0, ubCode 0.38.0; inline spelling `links_from_match`) links a result to the test need whose title equals the result's case name. A test marker's title is its Pester path (SC-073e).

**Scope Decisions**:
- **Match on the title** (author, 2026-10-26): a test's title is its Pester path, with no path field of its own, so that the `It` name, the title and the path are not three texts saying the same. sphinx-needs 9.1 and ubCode 0.38 both accept `title` as a `join` field. codelinks filling the path from the `It` it annotates was dropped: it would be a second upstream change on top of the open SC-073a pull request.
- **No comma and no backslash in a traced test's name**: a `join` splits its values on `,`, so a name with a comma could match a fragment of another test's name; and `testrunner.ps1` turns every `\` in a case name into `/` for Codecov, so a name with a backslash never matches its title. The px-proxy `It`s with either in their name are renamed, and the build refuses a test title with either.
- **The status is a derived field, not a link**: on a test from its results (none means not run), on a requirement from its tests (none means untested). ubCode 0.38 computes `collect`, `any` and `all` as well as `join` and `copy` (checked 2026-10-26).
- **The status is a `min` over an ordered `result`** (the agent's call): a derived field with nothing to read has no value, and a `default` is refused beside `derive`, so *not run* cannot be a rule's fallback. `result` is declared with the enum failed, error, passed, skipped, disabled, not run, worst first; a test holds `result = "not run"` of its own, and its `verdict` is the `min` over its results and itself, so any result outranks *not run*. A requirement's `verdict` is the `min` over its tests' verdicts. *Untested* never shows: the gate refuses a requirement without a test.
- **Stable result IDs** (the agent's call): `deterministic_case_ids` derives a result's ID from its file and case name, not from its failure text, so the ID stays when a test fails differently. The IDs are lowercase, so `id_regex` allows lowercase.
- **The gate covers the `Describe`s SC-073e traced** (the agent's call): 22 of the 84 `It`s in `px-proxy.Tests.ps1` carry markers, all of six `Describe`s and none of the others. The rule that a result links its test selects the results of those six by name; it covers the whole file once every `It` carries a marker (SC-073e).
- **Not run is no failure**: a test that does not run in CI, such as a WSL integration test, shows not run. The gate fails on a result from a traced test file that links no test (a renamed `Describe` or `It` whose marker was not updated), and on a requirement without a test (SC-073e).
- **`test/bin/testrunner.ps1` stays as it is**: `junit.xml` is read as Pester writes it.
- **All results on a page of their own, the px-proxy view on its Traces page** (author, 2026-10-26): `test-file` with `:auto_suites:` and `:auto_cases:` is the only way both readers create result needs, and it creates one for every case in the report; neither reader filters before creating them. `docs/test-results.md`, titled "Test results" in the Development section, holds the report; the px-proxy Traces page shows tables filtered to px-proxy's tests.
- **A build without a report shows not run**: `test_reports.report_missing` is suppressed, so that a local build needs no test run first. In CI the documentation job downloads the report the test job uploads, and a missing report fails that step (the agent's call).
- **Short entries under px-proxy** (author, 2026-10-26): the runbook's table of contents names its two pages "Requirements" and "Traces"; the pages keep their headings, so search results and browser tabs still name the tool.
- **Coverage under Development** (author, 2026-10-26, beyond this item's summary): the Development section links the develop branch's coverage on Codecov.
- **The ubCode half of the first two criteria is a recorded gap** (author, 2026-10-26): ubCode 0.38 reads no PowerShell markers, so it holds no implementation or test needs for px-proxy, and its results link no test and show no status. It reads the configuration (`[test_reports]`, the `join`, the derived fields, `schemas.json`) and closes the gap with SC-073a's parity port, as SC-073a records; the item does not wait for it.

**Acceptance Criteria**:
- [ ] Each px-proxy test result links its test, in ubCode and in the Sphinx build
- [ ] Tests and requirements show untested, not run, passed or failed, alike in both readers
- [ ] A renamed `It` whose marker was not updated fails the documentation build
- [ ] `test/bin/testrunner.ps1` is unchanged
- [ ] The px-proxy Traces page shows the status of each requirement and test; the results of the whole suite are on "Test results" in the Development section
- [ ] The Development section links the coverage of develop on Codecov
