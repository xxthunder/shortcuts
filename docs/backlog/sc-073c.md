# [SC-073c] px-proxy requirements, and the ADR that constrains them

**Status**: In Progress
**Priority**: Medium
**Component**: `docs/requirements/px-proxy.md` (new), `docs/architecture/adr/`, `pyproject.toml`, `uv.lock`
**Depends on**: [SC-073b](sc-073b.md), [SC-073g](sc-073g.md); XAS-044b in xxthunder-agentic-skills

**Summary**:
As the maintainer, I want px-proxy's current behaviour written down as requirement needs, with ADR-0008 linked to the requirements it constrains, so that code, tests and decisions trace to what px-proxy does now.

**Description**:
The requirements are drafted by an agent from a prompt that cites this item's and [SC-073](sc-073.md)'s scope decisions, from what is true now: `tools/proxy/px-proxy.ps1`, its tests and `docs/runbooks/px-proxy.md`. The closed items that touched px-proxy (listed in [SC-073](sc-073.md)) are read as hints to what px-proxy was meant to do, not mapped onto requirements. The author approves the requirements before anything is written.

All ADRs move to need headers in one migration (XAS-044b). Backlog items keep their format: they are history, not needs (XAS-044, author 2026-11-07).

**Scope Decisions**:
- **Requirement ID scheme**: `REQ_PX_<TOPIC>`, decided with the first requirements (2026-10-24).
- **Thin slice first** (author, 2026-10-24): three requirements (`REQ_PX_FILES`, `REQ_PX_UPSTREAM`, `REQ_PX_REMOVE`) come with the first pull request of SC-073b, so the codelinks pull request (SC-073a) can link a published example. They were drafted from the code, the tests and the runbook and approved by the author, not bootstrapped by the XAS-044d scan; the scan follows in this item.
- **A prompt, not the XAS-044d scan** (author, 2026-11-07): this item does not wait for a scan skill. The rules the scan would carry already stand in the record, and a skill pays off only when the same prompt repeats; px-proxy and wsl-manager are drafted by prompt, and XAS-044d decides from those two runs whether a skill is worth it.
- **codelinks from `sc-073a-preview-3`** (author, 2026-11-11): the tag on 1d979c0, the latest commit of the SC-073a pull request (useblocks/sphinx-needs#2380), rebased onto upstream `master` of 2026-11-09. It replaces `sc-073a-preview-2` as the first task of this item, before the migration and the requirements, so they are written against the codelinks the pull request proposes now. A marker that the newer codelinks reads differently is fixed in that task.
- **Behaviour that cannot be determined** is listed in this item, not guessed.
- **The requirements, approved** (author, 2026-11-11): drafted in the Q&A before the plan, so the loop writes exactly this text, ordered by capability. The three requirements of the thin slice stay as they are.
  - *Endpoint and files*
    - `REQ_PX_ENDPOINT` **px listens on 127.0.0.1:3128 only**: the generated `px.ini` always sets `listen = 127.0.0.1` and `port = 3128`; `server`, `pac`, `listen`, `port` and `auth` are dropped from px-user.ini, so nothing there can change them.
    - `REQ_PX_FILES` (kept) px's files live in the user profile.
  - *Commands*
    - `REQ_PX_INSTALL` **install installs px only when it is missing**: `install` creates the data directory and seeds the px-user.ini template; when no `px` command resolves, it installs px with Scoop and writes a marker that px-proxy installed it. It writes no `px.ini`.
    - `REQ_PX_START` **start rewrites the config and runs exactly one px**: `start` is the default action. Without a px executable it fails before writing anything; otherwise it rewrites `px.ini`, stops a running px, and starts the windowless `pxw` with that `px.ini`, in the data directory.
    - `REQ_PX_STOP` **stop ends px and its logon start**: `stop` asks px to quit and force-kills px and pxw that still run after that; with no px running it changes nothing. Either way it deletes the logon start.
    - `REQ_PX_REMOVE` (kept) remove leaves only the user's overrides.
    - `REQ_PX_TEST` **test checks the endpoint over HTTPS and names the failure**: `test` sends an HTTPS request to `https://www.google.com` through the endpoint, with a 20-second timeout. It reports the HTTP status on success, and on failure names the cause: authentication to the upstream (407), the TLS revocation check, a certificate, or another error. A failure ends the run with exit code 1.
  - *Upstream*
    - `REQ_PX_UPSTREAM` (kept, as SC-087 left it) px takes the upstream proxy from Windows unless a host is given.
  - *Start at logon*
    - `REQ_PX_LOGON` **a successful start makes px start at logon**: only after px was launched, `start` registers a logon start that runs `pxw` with the same `px.ini`, without a lookup. A failed `start` leaves an existing entry alone, and the restart inside `start` keeps it.
  - *Settings*
    - `REQ_PX_SETTINGS` **px-user.ini overrides the defaults in its [settings] block**: the `[settings]` of `px.ini` are the defaults `log = 0`, `workers = 1`, `threads = 32`, `idle = 300`, `socktimeout = 300.0`, `proxyreload = 60` and `foreground = 0`, with px-user.ini's `[settings]` merged on top. Other sections, comments and inline comments in px-user.ini are ignored.
    - `REQ_PX_USER_TEMPLATE` **px-user.ini starts as a template that changes nothing**: `install` and `start` write px-user.ini only when it is missing: every overridable key, commented out, at its default.
  - *Running the tool*
    - `REQ_PX_EXIT` **the exit code says whether the action succeeded**: 0 on success; on failure an error that names the action, and 1.
    - `REQ_PX_WAIT_KEY` **the window stays open until a key is pressed**: by default px-proxy waits for a key before it exits, after a failure too, so a window opened from Keypirinha stays readable. `-WaitForKey:$false` turns it off; in CI and tests it never waits, and a host without an interactive console does not fail.
- **Markers for its own requirements only** (author, 2026-11-11): the schema fails the build for a requirement without an implementation or a test, so this item marks the functions that implement its new requirements and the `It`s that test them, as the thin slice did. The rest stays with [SC-073e](sc-073e.md): helpers no requirement names, `It`s outside every requirement, the check for unmarked functions and the `AGENTS.md` rule.
- **ubCode is compared by the author** (author, 2026-11-11): the fifth criterion is the author's step on the pull request's branch, comparing ADR-0008's `constrains` links in ubCode with the Sphinx build. `ubc check` in CI stays with [SC-073b](sc-073b.md): whether ubc 0.39 reads PowerShell markers is not known here, and a `ubc check` that cannot see them would fail on every requirement.
- **Open points** (2026-11-11), behaviour this item does not determine:
  - The logon start is written by `Register-Autostart` in `lib/utils`, which no codelinks project traces; `REQ_PX_LOGON` says what the entry does, not where it lives.
  - What the empty `auth =` in `px.ini` does is px's behaviour, not px-proxy's, and no requirement.
  - px detection in `setProxy.ps1` and WSL's use of px belong to setProxy and wsl-manager, not to px-proxy's requirements.
- **No item links to a requirement** (author, 2026-11-07, XAS-044): the git history links an item to the changes it made.
- **ADR-0008** links the requirements it constrains; its context item ([SC-087](sc-087.md)) stays a plain link to the item page. ADR-0005, which it superseded, links none: a superseded decision constrains nothing (author, 2026-11-11).
