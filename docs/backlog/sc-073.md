# [SC-073] Traceability with sphinx-needs, ubCode and codelinks: px-proxy first

**Status**: In Progress
**Priority**: Medium
**Component**: `ubproject.toml` (new), `conf.py` (new), `docs/requirements/` (new), `docs/architecture/`, `tools/proxy/`, `.github/workflows/`
**Related**: XAS-044 in xxthunder-agentic-skills (requirements in the design record, ADR headers as needs), [SC-065](sc-065.md) (devcontainer)

**Summary**:
As the maintainer, I want shortcuts to carry its requirements, ADRs, architecture, code and tests as one traced sphinx-needs model, read alike by ubCode and the Sphinx build and checked in CI, so that shortcuts shows on a real open-source repository how the useblocks tooling works.

**Description**:
shortcuts becomes an open-source reference project for sphinx-needs, ubCode and sphinx-codelinks: a repository built with agents, with a backlog, ADRs and a C4 model, written in PowerShell. The repository and its published documentation are the deliverable; there is no live demo. useblocks welcomed contributions for what the tooling lacks (user day, 2026-10-23).

The traces:

| From | To |
|---|---|
| decision (ADR) | the requirements it constrains, the components it shapes |
| component (C4) | the requirements it realises |
| implementation (codelinks marker on a function) | requirement, component |
| test (codelinks marker on a Pester `It`) | the requirements it tests |
| test result (JUnit report) | the test it resulted from |

The levels are the ones of ASPICE and of useblocks/SPLed: a test points to the requirements it tests, a result to the test it resulted from. A requirement can therefore be tested but not verified, when its test did not run.

A requirement states what a tool does now; a closed item is history (XAS-044) and is not part of the model. SC-040 decided that px does not start at logon and SC-067 reversed it; code that pointed at SC-040 would be wrong today, code that points at the requirement is not.

The first slice is px-proxy: `tools/proxy/px-proxy.ps1` and its tests, `docs/runbooks/px-proxy.md`, [ADR 0005](../architecture/adr/0005-px-starts-at-logon-from-the-last-config.md), and the items that touched it ([SC-036](sc-036.md) and its substories, [SC-040](sc-040.md) to [SC-049](sc-049.md), [SC-051](sc-051.md), [SC-059](sc-059.md), [SC-060](sc-060.md), [SC-067](sc-067.md)). The other tools follow one at a time, in items of their own.

**Scope Decisions**:
- **Items are not needs** (author, 2026-11-07, XAS-044): a backlog item is history, not product knowledge. It stays a plain Markdown page, is no need, and links to no requirement. Which requirements an item changed is in the git history: the commit that closes the item changes the requirements with it.
- **One configuration**: `ubproject.toml` at the repository root, read by ubCode and `ubc` directly and by Sphinx through `needs_from_toml`, `src_trace_config_from_toml` and the `[test_reports]` section, as in useblocks/SPLed. It is also the switch XAS-044 keys on.
- **Only what both readers understand**: no Sphinx-only directive or needs function.
- **A missing trace fails the build**: Sphinx with `-W` and `ubc check` in CI.
- **Rules apply per tool**: a rule on code ("every function is traced") applies only to a tool that has a requirements file. "Every requirement is implemented and tested" holds from the first slice.
- **Implementation and tests trace through codelinks markers**, once codelinks reads PowerShell: a marker above a function or a Pester `It` names the requirements it implements or tests.
- **A result finds its test by matching**: both readers read `test/out/junit.xml` directly, and a derived `join` (sphinx-needs 9.1, ubCode 0.38) links each result to the test whose Pester path (`Describe.Context.It`) equals the result's case name. Whether a test or requirement is untested, not run, passed or failed is a derived field, not a link.
- **The documentation is published on GitHub Pages** (the agent's call, not discussed).
- **Two purposes** (author, 2026-11-06): the traced model is the reference project for the useblocks tooling and the documentation of the tools themselves.
- **Only PowerShell is traced** (author, 2026-11-06): functions in `.ps1` files and Pester `It`s carry markers; `.bat` and `.cmd` wrappers do not. The Bash scripts under `lib/wsl/scripts/` stay untraced too (the agent's call, not discussed).
- **px-proxy is finished first** (author, 2026-11-06): the other tools follow, one item each, only after this item is closed, so they copy a settled pattern.
- **A tool's requirements file is ordered by capability** (author, 2026-11-06): one section per capability, one requirement per command or behaviour, so a reader finds both what a tool can do and what a command does.
- **Requirements are derived from the Done items and checked against the code**: the items show what a tool was meant to do; the code and tests show what it does now, and where they differ the code wins and the gap is reported to the author.
