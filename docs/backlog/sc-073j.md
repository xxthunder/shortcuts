# [SC-073j] WSL Manager requirements

**Status**: Open
**Priority**: Medium
**Component**: `docs/requirements/wsl-manager.md` (new), `docs/traceability/wsl-manager.md` (new), `tools/wsl-manager/wsl-manager.ps1`, `lib/wsl/` and their tests, `docs/wsl-manager.md`
**Depends on**: [SC-073c](sc-073c.md)

**Summary**:
As the maintainer, I want WSL Manager's current behaviour written down as requirement needs, traced to its code and tests, so that the largest tool of shortcuts is covered by the traced model.

**Description**:
`docs/wsl-manager.md` (about 1050 lines) documents a TUI and CLI that manage WSL distributions (list, clone, update, remove, terminate), set up users, the corporate root CA and the proxy, install Docker or rootless Podman, and configure dev containers with DevPod or VS Code (SSH agent, git, SSH config). The code is `lib/wsl/` with about a dozen modules and their unit and integration tests. Its size likely asks for several items; the first step of this item is to propose the split by capability.

**Scope Decisions**:
- **Requirements first, ubCode when it is ready** (author, 2026-11-14): this item does not wait for the rest of px-proxy (SC-073a, SC-073b, SC-073e, SC-073f). The only thing that waits is ubCode, which reads no PowerShell before its release with useblocks/ubcode#4750; the Sphinx build traces the markers with the codelinks pin of the day, and the ubCode comparison stays with [SC-073a](sc-073a.md). The pattern SC-073c settled (requirements by capability, markers on the functions and `It`s that implement and test them, ADRs that constrain them) is the one to copy.
- **Requirements are drafted by prompt and approved before anything is written**, as in [SC-073c](sc-073c.md): from what is true now, the code, its tests and the documentation; the Done items that touched the tool are hints, not a source. Behaviour that cannot be determined is listed in this item, not guessed.
- **Markers for its own requirements only**, as in SC-073c: the functions that implement a requirement and the `It`s that test it; the rest of the tool's functions wait for the check for unmarked functions in [SC-073e](sc-073e.md).
- **The split comes first** (the agent's call, not discussed): before any requirement is drafted, the author approves a split of WSL Manager into capabilities, and each capability that is too large for one pull request becomes a substory of this item.

**Acceptance Criteria**:
- [ ] `docs/requirements/wsl-manager.md` states WSL Manager's current behaviour as requirement needs, ordered by capability, approved by the author
- [ ] Every requirement is implemented and tested: a codelinks marker on a function and on a Pester `It` traces to it, and the documentation builds with Sphinx `-W`
- [ ] The ADRs that constrain WSL Manager link the requirements they constrain
- [ ] WSL Manager's documentation links its requirements and traces page, as px-proxy's runbook does
