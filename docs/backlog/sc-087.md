# [SC-087] ✅ DONE - px takes the upstream proxy from Windows on every request

**Status**: Done (2026-11-11)
**Priority**: Medium
**Component**: `tools/proxy/px-proxy.ps1`, `tools/proxy/px-proxy.Tests.ps1`, `docs/runbooks/px-proxy.md`, `docs/requirements/px-proxy.md`

**Summary**:
As a user who moves between company sites, home office and VPN, I want px to ask Windows for the upstream proxy on every request so that px keeps working after the network changes, without running `start` again.

**Description**:
Today `start` resolves the upstream proxy once (`Resolve-PxUpstreamProxy`: `-ProxyHost`, then the PAC unless it says `DIRECT`, then the host of an `HTTP/<host>` Kerberos ticket with port 8080, then a prompt) and writes it into `px.ini` as `server = <host:port>`. The logon start reuses that `px.ini`. When the upstream changes (another site, abroad, VPN on or off), px keeps the old one until the user runs `start` again on the company network. The runbook says so under "Start at logon".

The sister setup [claude-setup](https://git.marquardt.de/projects/SWBASE039/repos/claude-setup) (`bin/setupPx.ps1`) writes `px.ini` with neither `server` nor `pac`. According to its comments, px then reads the Windows proxy settings and asks Windows (`WinHttpGetProxyForUrl`) for the proxy on every request, like the browser does, and `proxyreload = 60` makes it reread them. Its comments also name a case the pinned approach and px's own PAC engine get wrong: on a machine with home Wi-Fi and VPN, px's PAC engine takes the first IP of the host name, which can be the home address, and the PAC answers that with `DIRECT`.

The root-cause note in the runbook still holds: px must reach the real proxy host, which carries the Kerberos SPN, not the host that hands out the PAC. Windows evaluates the PAC and returns the real proxy (on the author's machine: `osde01proxy02.marquardt.de:8080`), so the new default keeps that.

Both setups write the same `%USERPROFILE%\.config\px\px.ini` and each adds its own Startup shortcut (`px-proxy.lnk` here, `px proxy.lnk` there). On a machine with both, the last run wins `px.ini` and two px compete for port 3128 at logon. Aligning the upstream strategy is the first step to one px setup; which repository owns it is agreed with the claude-setup maintainer and is out of scope here.

**Scope Decisions**:
- **No lookup without `-ProxyHost`** (the maintainer's call, 2026-11-10): `start` drops the whole lookup chain: the PAC evaluation, the Kerberos-ticket guess and the manual prompt. `-ProxyHost` is the only way to pin an upstream.
- **A new ADR supersedes ADR 0005** (2026-11-10): the logon start still reuses the last `px.ini`, but that `px.ini` no longer pins an upstream unless `-ProxyHost` was given. ADR 0005 gets the status "Superseded by" the new ADR.
- **`proxyreload` is a default, not tool-managed** (2026-11-10): `proxyreload = 60` goes into the built-in `[settings]` defaults, so `px-user.ini` may override it, and the runbook's `px-user.ini` table lists it.
- **`foreground = 0` comes along** (2026-11-10): `foreground = 0` joins the built-in `[settings]` defaults, as in claude-setup, so the two setups write the same settings.
- **A week of daily use before the merge** (2026-11-11): the author runs the change on Windows from the branch `feat/px-upstream-from-windows` of the downstream fork, whose vendored subtree holds a release candidate built from this branch. PR [#106](https://github.com/xxthunder/shortcuts/pull/106) merges at the end of the week (2026-11-13) if px works as expected. After the merge, the fork's branch is rebuilt from the real `release` commit before it merges there. The author ended the trial early on 2026-11-11: px worked as expected across the network changes, so #106 merges then.
