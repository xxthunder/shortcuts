# [SC-036] ✅ DONE - Corporate proxy for WSL without stored credentials

**Status**: Done (2026-07-16)
**Priority**: High
**Component**: `lib/wsl/proxy.ps1`, `lib/wsl/scripts/setup-proxy.sh`, `tools/proxy/setProxy.ps1`, `lib/utils/utils.ps1`, `docs/wsl-manager.md`
**Related**: [SC-007](sc-007.md) (setup-proxy — Basic auth), [SC-040](sc-040.md) (Windows-side px authenticating proxy)

**Summary**:
As a developer in a corporate environment with a Kerberos/NTLM proxy, I want `wsl-manager setup-proxy` to reach the internet from WSL without storing my credentials in environment variables where AI coding agents can read them.

**Description**:
SC-007's Basic mode embeds credentials in the proxy URL and exports them as `HTTP_PROXY=http://user:pass@proxy:port`. Every process in the shell — including AI coding agents — can read those creds via `/proc/*/environ`.

The original plan for this epic (see the superseded stories below) was to build a full Kerberos+px stack **inside** each WSL distro: install `krb5-user` and `px-proxy`, write `krb5.conf`/`px.ini`, run `kinit`, and auto-start px from `.bashrc`. That is a large, per-distro, per-machine apparatus.

[SC-040](sc-040.md) made that unnecessary for the common case. It runs **px on the Windows host**, where px authenticates to the corporate proxy using the current Windows logon session (SSPI: NTLM or Negotiate/Kerberos) and exposes a plain local proxy on `http://127.0.0.1:3128`. Because this machine runs WSL in `networkingMode=mirrored`, every WSL distro reaches that same `127.0.0.1:3128` — so one Windows-side px serves both worlds with **no credentials stored anywhere**, in Windows or in WSL.

The remaining work is therefore small: teach `wsl-manager`'s Auto proxy setup to detect a running Windows px (reusing `setProxy.ps1`'s `Test-PxProxyAvailable`) and let the user point WSL at it instead of the PAC-resolved corporate proxy. That is [SC-036f](sc-036f.md).

**Scope Decisions**:
- **Reuse the Windows-side px instead of building one per distro**: SC-040 already solves upstream authentication once, on the host, for every tool including WSL. Duplicating that stack inside each distro (krb5, kinit, px, ticket-expiry handling, teardown) is redundant given mirrored networking. The four in-WSL phases are dropped.
- **Mirrored networking is assumed**: WSL reaching `127.0.0.1:3128` on the host depends on `networkingMode=mirrored` (Windows 11 22H2+). Under default NAT mode this does not work; that scenario is out of scope (documented in the [px Proxy runbook](../runbooks/px-proxy.md)). If NAT-mode support is ever needed, the superseded stories remain a viable — if heavier — fallback and can be reopened.
- **Detection reuses `setProxy.ps1`**: `Install-WslProxy` already dot-sources `setProxy.ps1`, so `Test-PxProxyAvailable` is in scope with no new coupling. Detail lives in [SC-036f](sc-036f.md).
- **Auth prompt is Anonymous / Basic**: with the in-WSL Negotiate path gone, the WSL-side auth choice is simply whether the *corporate* proxy URL carries credentials. Targeting px is credential-less by construction (px authenticates on the host).

**Security properties (end state)**:
- No credentials in env vars or config files when px is used — px authenticates on the Windows host via the logon session (SSPI); WSL only ever sees `HTTP_PROXY=http://127.0.0.1:3128`, useless to anything off this machine.
- Basic mode remains available (Anonymous or user-supplied credentials) for a directly-reachable corporate proxy when px is not in play.
