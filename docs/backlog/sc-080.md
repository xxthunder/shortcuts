# [SC-080] update-scoop reports success for apps Scoop skipped

**Status**: Open
**Priority**: High
**Component**: `lib/scoop/scoop.ps1`, `tools/scoop/`

**Summary**:
As a user of the Scoop update helper, I want it to report an app as updated only when Scoop really updated it, so that I can trust "Update complete!" and know which apps I still have to close and update again.

**Description**:
Found on 2026-10-22 in the UAT of a downstream fork that vendors this repository as a subtree.

When an app is running, Scoop prints "Running process detected, skip updating." and still exits with 0. `Update-ScoopApp` checks only `$LASTEXITCODE`, so it prints "<app> updated successfully" and, at the end, "Update complete!". In the UAT this happened for autohotkey, pwsh and windows-terminal; `scoop list` still showed the old versions. sysinternals and vscode were updated once their processes were closed.

The same check gives a related false success: apps whose manifest Scoop cannot read appear in the list with an empty target version, e.g. `7zip (26.00 -> )`, and with `[A]ll` each of them is "updated successfully" although Scoop says "latest version".

**Scope Decisions**:
- **Compare the installed version before and after `scoop update <app>`** (suggested in the UAT): the exit code says nothing about a skipped update.

**Open Questions**:
- Should apps without a target version be left out of the list here, or in a separate item?
- Should the helper name the processes that block an update (pwsh, Windows Terminal, VS Code terminals)? The UAT asked for it in the README and in the helper's output.

**Acceptance Criteria**:
- [ ] An app whose installed version did not change is reported as not updated, with Scoop's reason when it gave one
- [ ] "Update complete!" appears only when every selected app was updated; otherwise the helper lists the apps that were not
- [ ] Unit tests cover an updated app, a skipped running app and an app already at the latest version, with `scoop` mocked
- [ ] All existing tests continue to pass
