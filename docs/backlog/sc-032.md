# [SC-032] Investigate split-pane TUI layout for WSL Manager

**Status**: Open
**Priority**: Low
**Component**: `lib/wsl/manager.ps1`
**Depends on**: [SC-016](sc-016.md)
**Related**: [SC-057](sc-057.md) (shipped the interim `Refresh list` entry; the findings below were established there), [SC-058](sc-058.md) (drops `-Expand` so a stale render wraps less; does not redraw)

**Summary**:
As a user, I want the WSL Manager TUI to have a split-pane layout (menu on the left, command output on the right) similar to lazygit, so that I can see command results alongside the menu.

**Description**:
PwshSpectreConsole provides `New-SpectreLayout -Columns` for side-by-side panels and `Invoke-SpectreLive` for real-time updates. However, `Read-SpectreSelection` (interactive arrow-key prompts) cannot run inside a `Invoke-SpectreLive` context: both take over terminal input/output and conflict with each other. This is a fundamental Spectre.Console limitation.

### Investigation needed

- Can `Invoke-SpectreLive` be paused/exited cleanly to hand control to `Read-SpectreSelection`, then resumed?
- Can command output be captured (e.g., via `Start-Transcript` or stream redirection) and displayed in a right-side panel after the prompt returns?
- Would Terminal.Gui (full TUI framework) be worth reconsidering despite the testability trade-off?
- Are there hybrid approaches: static split layout between commands, full-terminal prompt during selection?

### Findings so far (2026-09-14, PwshSpectreConsole 2.6.3)

Established while scoping SC-057, which needed the distribution table above the menu to stay current. They answer investigation questions 1 and 4 above; questions 2 and 3 remain open.

- **Nothing new in the module.** 2.6.3 is installed and is the latest on PSGallery (published 2026-03-02); it was already current when the TUI adopted Spectre on 2026-04-07. Everything below exists in that version.
- **`Read-SpectreSelection -TimeoutSeconds` is not a refresh mechanism.** It runs the prompt through `ShowAsync` with a `CancellationToken` polled every 200 ms (`Invoke-SpectrePromptAsync`) and cancels it after the interval, which would let a loop redraw. But it prints hard-coded `This prompt times out in N seconds...` and `Prompt timed out` messages, `SelectionPrompt` has no initial-selection property so every timeout throws the cursor back to the top and discards a typed search, and the `$null` return is indistinguishable from Ctrl+C.
- **`Read-SpectreSelection` cannot react to keys or redraw the table.** The prompt consumes every key through Spectre's `IAnsiConsoleInput`, and the panel above it lies outside the prompt's render region, so redrawing the table while the prompt is up corrupts the prompt's cursor bookkeeping.
- **A menu that owns its key loop inside `Invoke-SpectreLive` is the viable path.** The module's own `Invoke-SpectreLive` Example 2 (a file browser) is the pattern: a layout, a loop that drains `[Console]::KeyAvailable` / `ReadKey($true)`, handles Up/Down/Enter/Escape, updates layout cells, calls `$Context.Refresh()`. The table becomes a layout cell that can be updated on a timer or on a key, and the split-pane layout this item asks for is the same structure.
- **The hybrid in question 4 works when the loop is ours.** On Enter the loop returns from `Invoke-SpectreLive`, the command runs with the normal `Read-Spectre*` prompts on the full terminal, and the loop re-enters afterwards. The limitation "no `Read-SpectreSelection` inside live" only bites if the main menu keeps using `Read-SpectreSelection`.
- **Costs to budget.** Reimplement what `Read-SpectreSelection` gives for free (highlight, paging, wrap-around, type-to-search with highlight). Wrap `[Console]::ReadKey` in a mockable function and inject a key source so the loop is unit-testable; the `Show-WslMenu` tests are rewritten around it. `wsl.exe --list --verbose` costs 50-100 ms per call (5 runs measured), so a refresh on every key press would stutter; throttle to about 2 s, or fetch on a background thread job the loop polls.
- **What this means for the spike.** Build a throwaway live layout with a key loop and a 2 s table refresh, and let that decide between re-scoping the TUI onto the loop or keeping `Read-SpectreSelection` plus the `Refresh list` entry from SC-057.

### Findings (2026-09-15 to 2026-09-19): resize handling

Collected while diagnosing a report that the table renders wrongly after a window resize. The non-recovery part turned out to be a separate defect with its own root cause, fixed in [SC-058](sc-058.md); what remains for this item is the redraw-while-waiting part.

- **The manager draws once per command and has no resize path.** `Start-InteractiveMode` renders the panel, then blocks in `Read-SpectreSelection`. A resize during that block changes nothing on screen until the next command. Only a key loop that owns input can poll `$Host.UI.RawUI.WindowSize.Width` between keys and redraw when it changes; that is the same loop the table refresh needs, so resize handling is a third reason for the loop.
- **The width readings are trustworthy.** `RawUI.BufferSize.Width`, `RawUI.WindowSize.Width`, `[Console]::BufferWidth`, `[Console]::WindowWidth` and `[Spectre.Console.AnsiConsole]::Profile.Width` agreed with the window at every step of a loop that mirrors the manager (`Clear-Host`, Spectre render, `Read-SpectreSelection`), launched through a `.bat`, including immediately after a resize made while the prompt was up. A polling loop can rely on them.
- **Why redraws did not recover (fixed in SC-058).** Emitting a Spectre renderable to the pipeline hands it to PowerShell's formatting engine, which opens one format group per type for the whole script pipeline and keeps the console width it saw at the first draw. `Read-SpectreSelection`, `Clear-Host` and the `.bat` wrapper were all cleared by probes. Writing through `Out-SpectreHost` avoids the group. The live loop must draw the same way, or through `Invoke-SpectreLive`, never by emitting renderables to the pipeline.
