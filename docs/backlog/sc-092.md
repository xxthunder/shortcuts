# [SC-092] ✅ DONE - px falls back like the browser when the Windows automatic proxy setup finds no proxy (upstream PR)

**Status**: Done (2026-11-16)
**Priority**: Low
**Component**: [genotrance/px](https://github.com/genotrance/px) `px/wproxy.py`, its tests and docs (upstream, via the fork `xxthunder/px`)

**Summary**:
As a px user whose Windows proxy settings combine automatic setup (auto-detect, a setup script) with a manual proxy, I want px to fall back as the browser does when the automatic setup finds no proxy, so that px does not connect directly and fail where a firewall blocks direct connections.

**Description**:
SC-091 found the gap and documented it in the runbook. px 0.13.1 (`px/wproxy.py`, `Wproxy.__init__` on Windows) takes exactly one mode from `WinHttpGetIEProxyConfigForCurrentUser`: `fAutoDetect` gives `MODE_AUTO`, else a setup-script URL (`lpszAutoConfigUrl`) gives `MODE_PAC`, else a manual proxy (`lpszProxy`) gives `MODE_MANUAL`. Whatever the chosen mode does not use is dropped. In `MODE_AUTO`, `winhttp_find_proxy_for_url` calls `WinHttpGetProxyForUrl` with `WINHTTP_AUTOPROXY_AUTO_DETECT` only. When WPAD fails (`ERROR_WINHTTP_AUTODETECTION_FAILED`, 12180) or the setup script cannot be downloaded (`ERROR_WINHTTP_UNABLE_TO_DOWNLOAD_SCRIPT`), px returns `DIRECT`.

A probe with ctypes on the author's machine at headquarters on 2026-11-16 asked WinHTTP for the proxy of `https://www.google.com`: `AUTO_DETECT` alone failed with 12180; `CONFIG_URL` alone and both flags together returned the company proxy. WinHTTP tries auto-detection first when both flags are set, and the setup script when it fails.

px master (`devel`) has the same `wproxy.py` as 0.13.1, and no px issue covers this. px is MIT-licensed; its CI (`.github/workflows/ci.yml`) runs `make check` and pytest on Ubuntu and Windows on every pull request. Its `AGENTS.md` asks for one-line commit messages without AI attribution, and for `docs/changelog.md` and the affected docs on every user-visible change.

**Scope Decisions**:
- **Upstream, not a local patch** (the maintainer's call, 2026-11-16): px-proxy installs px unchanged; the fix goes to genotrance/px. px-proxy needs no change and does not wait for the release.
- **A fork and two pull requests** (the maintainer's call, 2026-11-16): the work happens in the fork `xxthunder/px`, cloned to `~/dev/xxthunder/px`. The closed loop's pull request stays inside the fork (feature branch into `devel`), carries the evidence package, and the fork's CI is the gate. The pull request to genotrance/px is separate and short, in px's style, without the evidence package.
- **No upstream issue** (the maintainer's call, 2026-11-16): the pull request to genotrance/px carries the description and the reproduction alone; px takes outside pull requests without an issue.
- **Text posted under the author's name is a draft first** (2026-11-16): the upstream pull request's title and body are shown to the author and posted after a go.
- **The manual proxy is a further fallback** (the maintainer's call, 2026-11-16). The behaviour, when px has neither `server` nor `pac` configured:
  1. Auto-detect on and a setup script set: px asks WinHTTP with both flags and the script's URL, so WPAD comes first and the setup script second.
  2. Auto-detect or a setup script that finds no proxy (WPAD fails, or the script cannot be downloaded): px uses the manual proxy with its bypass list when "Use a proxy server" is set; only without one does it connect directly, as today.
  3. Point 2 holds for the setup script alone too.
  4. Unchanged: the manual proxy alone, nothing set, and a setup script that answers `DIRECT`, which is an answer, not a failure.
- **Agent's calls** (2026-11-16): that WinINet, and so the browser, falls back to the manual proxy in this way is the agent's understanding, not verified on the author's machine, since that would mean changing its proxy settings. The tests mock the Windows API and run on Windows only, so the fork's CI runs them. The px docs follow px's `AGENTS.md`: the changelog, `docs/configuration.md` and `docs/architecture.md` as far as they describe the Windows proxy settings.
- **Prior art not used** (agent's call, 2026-11-16): WinHTTP's `WINHTTP_AUTOPROXY_ALLOW_STATIC` ("enables proxy detection via static configuration", Windows 10 1703 and later) might give the manual-proxy fallback from WinHTTP itself. Its exact behaviour is not documented, it needs a recent Windows, and it is aimed at `WinHttpGetProxyForUrlEx`, so px implements the fallback itself. The final reviewer reports that Chromium falls back to the manual proxy when the PAC fails (`ConfiguredProxyResolutionService`); not checked against the source.
